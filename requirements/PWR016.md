# PWR016 — Boot-Time Calibration, Adaptive Timeout & Near-Miss Detection

## Statement

The reliability tests (`power_cycle.py`, `reboot.py`) shall determine the
per-cycle boot-wait ceiling (`boot_timeout`) automatically rather than requiring
the operator to guess it, and shall correct it during the run:

1. **Calibration** — before the counted test, run `CALIBRATE_CYCLES` measurement
   cycles (default 5) and set `boot_timeout = max(observed) ×
   CALIBRATE_SAFETY_FACTOR` (default 1.5), capped at `boot_ceiling`. Setting
   `--calibrate 0` disables calibration and uses `--boot-timeout` directly.

2. **Adaptive raising / near-miss** — a small calibration sample can
   under-estimate the timeout for a DUT whose boot time is bimodal or
   occasionally long. Therefore, during the counted test, whenever a **PASSING**
   cycle's boot time is `>= NEAR_MISS_FRAC` (default 0.9) of the current
   `boot_timeout`, that cycle shall be flagged `near_miss`, and `boot_timeout`
   shall be raised on the fly to `boot_time × CALIBRATE_SAFETY_FACTOR` (capped at
   `boot_ceiling`). Setting `NEAR_MISS_FRAC = 0` disables adaptive raising.

3. **Reporting** — the calibration result (per-cycle measured times and the
   resulting timeout) and any near-miss cycles shall be recorded in
   `result.json` and surfaced in the HTML report, including a warning banner
   when one or more near-miss cycles occurred (the DUT boots close to the
   limit).

`power_cycle.py` and `reboot.py` shall implement this equivalently (FWK036).

## Rationale

A fixed boot timeout either wastes time (set too high) or produces spurious
`NO_BOOT` failures (set too low). Calibration removes the guess, but a 3–5 cycle
sample can miss a DUT's slow-boot tail: an observed run set the timeout to 104 s
from calibration (max 69.5 s × 1.5) while the real 100-cycle boot-time
distribution reached ~101 s, leaving only ~3 s of margin — a later 105 s boot
failed as `NO_BOOT` even though the DUT was healthy. Adaptive raising lets the
timeout self-correct the first time the DUT is seen booting near the limit,
turning that class of false failure into a warning instead. The near-miss flag
tells the operator the timeout was tight and the DUT boot time is borderline.

## Scope

`src/python/power_cycle.py`, `src/python/reboot.py`,
`src/python/liveness.py`, `src/python/report.py`, and the
`CALIBRATE_CYCLES`, `CALIBRATE_SAFETY_FACTOR`, `BOOT_CEILING_SEC`,
`NEAR_MISS_FRAC` keys in `src/python/config.py`.

## Implications

1. The `boot_timeout` recorded in `result.json` `config` is the **final**
   (possibly adaptively-raised) value; the calibration section records the
   originally-calibrated value, so both are visible.
2. Adaptive raising only ever **increases** the timeout and never above
   `boot_ceiling`; when already at the ceiling, the near-miss is still logged.
3. A near-miss is not itself a failure — the cycle still PASSes.
4. Non-compliance must be corrected before merge.

## Verification

Code Review: confirm calibration sets `boot_timeout = max × factor` capped at
the ceiling; confirm a PASSING cycle at `>= NEAR_MISS_FRAC` of the timeout flags
`near_miss` and raises the timeout (capped); confirm the report shows the
calibration values and a near-miss banner; confirm `reboot.py` behaves
equivalently.
