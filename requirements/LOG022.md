# LOG022 — ISO 8601 Timestamp Consistency

## Statement

All timestamps shall use the local time of the DUT and ISO 8601 format,
without a timezone offset (the DUT's local timezone is recorded once in
the log header per LOG005). Two representations are used:

1. **Filenames and directory names** — ISO 8601 **basic** format
   `YYYYMMDDTHHmmss` (e.g. `20260601T174545`). The `T` separator is
   mandatory. Basic format is required because the `:` character is
   illegal in filenames on Windows.

2. **JSON time fields and log-entry content** — ISO 8601 **extended**
   format `YYYY-MM-DDTHH:MM:SS` (e.g. `2026-06-01T17:45:45`). Extended
   format is used because it is more readable and `:` is permitted
   inside file content. (The human-readable log-line prefix defined by
   LOG014, `[YYYY-MM-DD HH:MM:SS]`, is unchanged.)

No timezone offset (`Z` or `±HH:MM`) is appended; all timestamps are DUT
local time by definition.

## Rationale

Codifies the decision after BUG0019. ISO 8601 ensures unambiguous parsing
across tools, locales, and shells; the bare 14-digit `YYYYMMDDHHmmss`
format used previously was visually ambiguous (the `T` separator fixes
this). Using DUT local time consistently — for both filenames and JSON —
means the same event shows the same wall-clock value everywhere, avoiding
the earlier inconsistency where filenames were local time but JSON fields
were UTC (`Z`). A single recorded timezone line in the log header
(LOG005) preserves the absolute reference without cluttering every
timestamp with an offset.

## Scope

All scripts and shared libraries in the framework.

## Implications

- Non-compliance must be corrected before merge.
- Filenames use basic format; JSON time fields and log content use
  extended format. Both are DUT local time with no offset.
- Implementations must derive both forms from the same local clock so the
  basic and extended representations of one event always agree.
