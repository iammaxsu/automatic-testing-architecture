# LOG026 — Session State Location and Target-Count Authority

## Statement

Session state used for resume (LOG023) shall be stored **inside the logs
tree**, at a stable per-DUT path
`logs/<dut>/<test>_session.json`. Two consequences are normative:

1. **Deleting the logs tree is a complete reset.** After the operator
   removes `logs/` (or the per-DUT subtree), the next run shall behave
   exactly as a first run: new `session_id`, iteration count starting at 1,
   and the operator-requested iteration count in force.
2. **The requested iteration count is authoritative.** When an operator
   requests an iteration count that differs from the incomplete session's
   planned count `m`, the framework shall start a **new** session using the
   requested count. It shall not silently continue the old session's `m`.
   Resume applies only when the requested count matches the session's `m`
   (or no count is explicitly requested).

A run shall also provide an explicit override (e.g. `--new-session` /
`-v NEW_SESSION:True`) that forces a new session regardless of state.

## Rationale

Resume must never surprise the operator into running the wrong test. Two
failure modes motivated this requirement, both observed in practice:

- Session state kept outside the logs tree survives a `rm -rf logs/`, so
  the documented "clean slate" gesture silently did nothing.
- Reusing the stored `m` on resume meant that after interrupting a
  100-iteration run, requesting 300 iterations ran only the 100 remaining
  from the old plan and stopped — the operator did not get the test they
  asked for.

Anchoring state in the logs tree gives the operator one obvious, discoverable
reset mechanism (delete the folder), and making the requested count
authoritative means the command line always describes what will happen.

## Scope

All test runners that support resume, in every language: the Python
reliability runners (`power_cycle.py`, `reboot.py`), the bash test scripts,
and the Robot Framework suites (`src/robot/`). The `<dut>` component follows
LOG025; `<test>` is the test name used in artefact names (LOG017).

## Implications

1. The session file is written atomically (tmp + rename) after every
   iteration, per LOG023.
2. Runners resolve the session path from the same log root they write
   artefacts to, so a custom log root (e.g. `--out` / `-o`) moves the session
   state with it.
3. On a count mismatch the runner shall log, at WARN, that a new session is
   starting and why.
4. A completed session (`status: complete`) is never resumed; the next run
   starts a new session.

## Verification

Automated Test:
1. Start an N-iteration run, interrupt it after k iterations, re-run with the
   same N: the run resumes at k+1 and stops at N.
2. Delete the logs tree, re-run with a different count M: a new session runs
   exactly M iterations.
3. Without deleting logs, request a different count M against an incomplete
   session: a new session is started for M (a WARN is logged), not the old
   plan.
