# LOG026 — Bounded Auto-Resume and Explicit Session Announcement

## Statement

Every run shall announce, **before the first iteration**, whether it is a
NEW session or is RESUMING an existing one (LOG023). The announcement shall
state the `session_id`, the session directory, the iteration range this run
will execute, and — when resuming — how many iterations were already
recorded and that this run appends to the same `result.json`.

Auto-resume shall **not expire by default**. An incomplete session shall
remain resumable regardless of how much wall-clock time has passed.

An optional age bound shall be available for operators who want one:
`RESUME_MAX_AGE_HOURS` / `--resume-max-age HOURS`. When set to a positive
value, a session whose `updated_at` is older than that window shall be
treated as abandoned — the run shall start a new session and report each
skipped session and the reason on the console.

Resolution order shall be:

| Order | Input                     | Effect                                        |
|-------|---------------------------|-----------------------------------------------|
| 1     | `--new-session`           | always start a new session                    |
| 2     | `--resume`                | resume an incomplete session at any age       |
| 3     | `--resume-max-age HOURS`  | auto-resume only within HOURS                 |
| 4     | (default, `-1`)           | auto-resume at any age                        |

`--new-session` and `--resume` together shall be rejected as a usage error.
`--resume-max-age 0` shall disable auto-resume entirely; a negative value
(the default) shall leave auto-resume unbounded.

## Rationale

LOG023 made an interrupted run resumable, but reported the decision as a
single parenthetical `(RESUMING)` among twenty startup fields. Whether a
run is new or resumed is the single most consequential fact about it — it
decides how many iterations actually execute and which `result.json` grows.
Buried in a field list, it is missed.

The observed consequence is that operators learn to `rm -rf logs/` before
every run as a defensive ritual, purely to be certain of a clean start.
That works — session state lives only under `--out` (LOG025), so deleting
it does force a new session — but it destroys prior results to obtain a
guarantee the tool should simply have stated outright. Announcing the
decision in a banner removes the need for the ritual; the ritual itself
keeps working unchanged for operators who prefer it.

**Why age-based expiry is off by default.** An earlier draft of this
requirement expired sessions after 24 hours, reasoning that a long-idle
session was probably abandoned. That reasoning does not survive contact
with how endurance tests are actually run: a multi-thousand-cycle test
routinely spans a weekend, and a four-day public holiday is normal bench
practice. Under a 24-hour bound, coming back on Tuesday would silently
start over rather than finish the run — the exact failure this requirement
exists to prevent, in the opposite direction and with real cycles lost.

Wall-clock age is therefore not evidence of abandonment for this workload,
and must not be treated as such by default. The bound remains available
(`--resume-max-age`) for benches where a stale session genuinely is noise,
but the operator opts in. The banner, not a timer, is what protects against
an unintended resume.

BUG0041 fixed the adjacent case where an *explicit* `--cycles` disagreed
with the resumable session. This requirement covers the case where the
operator passes nothing at all — the far more common path.

## Scope

| Applies to                       | Notes                                            |
|----------------------------------|--------------------------------------------------|
| `power_cycle.py`, `reboot.py`    | the LOG023 resumable multi-iteration tests       |
| `function.resolve_session()`     | the shared decision point                        |
| `run_tests.sh`                   | passes `--resume` / `--resume-max-age` through   |
| Ansible orchestration            | non-interactive; flags only, never a prompt      |

Single-run tests with no iteration counter (`disk_test.sh`, `net_test.sh`,
`dev_detect.sh`) are out of scope — they have no session to resume.

## Implications

1. `resolve_session()` gains `max_age_hours` and `force_resume` parameters
   and returns an additional `skipped` list describing incomplete sessions
   passed over for age, so the caller can report them.
2. Session age is derived from `updated_at`, falling back to `started_at`,
   then to `meta.json`'s mtime — a session written by an older build
   without timestamps is still aged rather than treated as ageless.
3. The decision is never made interactively. FWK024 requires
   non-interactive operation under Ansible; a TTY prompt would hang an
   automated run. The banner gives the same protection without blocking.
4. A session skipped for age is **skipped, not deleted or rewritten**. Its
   directory and `meta.json` remain untouched and it stays resumable via
   `--resume`, preserving FWK028's canonical record.
5. Deleting the output directory remains a valid way to force a clean
   start, and is unaffected by this requirement — session state lives only
   under `--out` (LOG025). `--new-session` does the same without destroying
   prior results, and is preferred.
6. `--out` is resolved relative to the **process working directory**, not
   the script's location. An operator who deletes `logs/` in one directory
   and launches the run from another has not cleared the state the run will
   use. The banner's `Directory:` line names the resolved path, making this
   visible rather than latent.

## Verification

`src/python/resolve_session_unittest.py` covers the full decision matrix
over `resolve_session()`, with no GPIO, SSH, or DUT required:

```bash
cd src/python && python3 -m unittest resolve_session_unittest -v
```


| Case                                  | Expected                        |
|---------------------------------------|---------------------------------|
| incomplete session 2 h old            | resumes, `start_n = n + 1`      |
| incomplete session 4 days old         | resumes (default: no expiry)    |
| `config.RESUME_MAX_AGE_HOURS`         | negative — expiry off by default|
| 50 h old + `--resume-max-age 24`      | new session, 1 skip reported    |
| 50 h old + `--resume-max-age 24 --resume` | resumes the old session     |
| fresh session + `--new-session`       | new session                     |
| `--resume-max-age 0`                  | never auto-resumes              |
| `--resume-max-age -1`                 | resumes at any age              |
| `meta.json` without timestamps        | ages by mtime, resumes if fresh |
| complete session (`n == m`)           | ignored, not reported as a skip |
| skipped session's `meta.json`         | unchanged on disk               |
| target mismatch (LOG025)              | still raises                    |
| explicit `--cycles` mismatch (BUG0041)| still raises                    |

Console verification: a dry run with a seeded stale session shows the
`NEW session` banner plus the skip warning; the same run with `--resume`
shows the `RESUMING` banner with the completed-cycle count.
