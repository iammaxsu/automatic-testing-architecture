# DET013 — Snapshot Mode and Machine-Readable Per-Run Result

## Statement

The device-detection scripts (`dev_detect.sh`, `dev_detect.ps1`) shall
support two mutually exclusive run modes:

1. **Standalone mode** (default, no flag) — unchanged from today's
   behaviour: the script owns its persistent loop, installs its own
   autorun mechanism (systemd on Linux, Task Scheduler on Windows),
   and triggers its own `reboot`/`poweroff` between passes until the
   target count is reached.

2. **Snapshot mode** (`--snapshot-only` on `.sh`, `-SnapshotOnly` on
   `.ps1`) — the script shall run exactly **one** detection-and-compare
   pass and exit. In this mode it shall **not** install or modify any
   autorun mechanism, and shall **not** call `reboot`, `poweroff`, or
   any power-state change. Loop count and power cycling are owned by the
   external orchestrator (`power_cycle.py` / `reboot.py`).

In **both** modes, each pass shall additionally write one
machine-readable JSON sidecar file alongside the existing `.log` /
`.txt` / `.diff` artefacts, without altering or replacing them. The
sidecar is the canonical per-pass record (FWK028); existing text logs
remain as human-readable views.

The process exit code shall encode the pass outcome:

| Outcome | Exit code | Meaning                                        |
|---------|-----------|------------------------------------------------|
| Pass    | `0`       | Verified: output matches an existing golden    |
| Fail    | `1`       | Deviation from the existing golden             |
| Error   | `2`       | Detection could not run (e.g. tool missing)    |
| INIT    | `3`       | No golden existed; one was just created. **Not** a verified pass — the orchestrator should record it but exclude it from pass/fail statistics. |

The JSON sidecar's `result` field shall carry the matching four-state
value (`Pass | Fail | Error | INIT`); INIT shall never be collapsed
into `Pass`, so that exit code and sidecar always agree.

## Rationale

Device detection must be runnable both standalone (manual/ad-hoc, no
control node) and under orchestration (driven by `power_cycle.py` over
SSH). Today the two scripts hard-wire their own reboot loop, which
collides with a relay-driven orchestrator that already owns power
cycling. Snapshot mode cleanly hands loop control to the orchestrator
while preserving the standalone path the scripts must keep.

INIT is a distinct outcome, not a Pass: on first run the golden is
merely captured from whatever hardware is present, so nothing was
actually verified — a faulty part present at that moment would be
baselined as "correct". Conflating INIT with Pass would let a silently
re-created golden (e.g. after a reimage or disk swap) inflate a
burn-in pass rate with runs that verified nothing. A separate exit code
and result value lets the orchestrator account for this honestly.

The JSON sidecar exists because the orchestrator records each pass into
its own canonical `result.json`; scraping PASS/FAIL out of free-form
text logs is brittle. A structured per-pass record (plus the exit code)
is the stable contract between detection script and orchestrator, and
is the prerequisite for any rendered cross-run report (heatmap /
Pareto) per FWK028.

## Scope

| Artefact          | Standalone mode        | Snapshot mode (`--snapshot-only`) |
|-------------------|------------------------|-----------------------------------|
| autorun install   | yes                    | **no**                            |
| reboot / poweroff | yes (until count met)  | **no**                            |
| passes per invoke | 1 (loop across boots)  | 1 (orchestrator re-invokes)       |
| text `.log/.txt/.diff` | written           | written (unchanged)               |
| JSON sidecar      | written                | written                           |
| exit code         | result-encoded         | result-encoded                    |

## Implications

1. A new flag is added to each script; absence of the flag preserves
   today's exact behaviour (backward compatible).
2. The autorun-install and reboot/poweroff blocks must be guarded so
   they are skipped under `--snapshot-only`.
3. A JSON sidecar is emitted per pass. Minimum fields:
   `schema_version`, `session_id`, `k`, `m`, `result`
   (`Pass | Fail | Error | INIT`), `timestamp`, and paths
   (`snapshot_path`, `golden_path`, `diff_path` when present).
   Per-component results are added in a later requirement (the
   per-component comparison work); this requirement only mandates the
   overall `result` field plus a forward-compatible `components` object
   (may be empty for now).
4. Exit codes are standardised across both scripts per the table in the
   Statement.
5. Each script shall provide a `--help` / `-h` (`-Help` on `.ps1`) that
   lists every accepted flag, its default, and the standalone-vs-snapshot
   distinction, then exits `0` without running detection. No flag may
   exist that is undocumented in this output.
6. A prose reference, `docs/dev_detect.md`, shall document the flags
   shared by both scripts, the JSON sidecar schema, and the exit-code
   table — i.e. the cross-script and orchestrator-integration knowledge
   that per-script `--help` cannot cover.
7. `power_cycle.py` / `reboot.py` may invoke the script over SSH after
   confirming the DUT is alive, read the exit code, and ingest the JSON
   sidecar into `result.json`. (The orchestrator side is a separate
   work item, not part of this requirement.)

## Verification

Automated Test:
- Run with `--snapshot-only`: assert exactly one pass ran, no autorun
  service/task was installed, no reboot/poweroff was issued, the JSON
  sidecar exists and parses, and the exit code matches the result.
- Run without the flag: assert today's standalone behaviour (autorun
  installed, loop/reboot path taken) is unchanged, and the JSON sidecar
  is additionally present.
- First run on a clean DUT: assert `result: INIT` and exit code `3`.
- Second run, unchanged hardware: assert `result: Pass` and exit code `0`.
- Inject a golden mismatch: assert `result: Fail` and exit code `1`.
- Run `--help`: assert every flag accepted by the parser appears in the
  output and that detection did not run.

### Status of verification (2026-06-23)

`dev_detect.sh`: now has an automated test harness,
`src/bash-shell/test_dev_detect.sh`. It runs the real script with a PATH shim
in front of `sudo`/`reboot`/`poweroff` (so autorun installs and
reboot/poweroff are observed, never actually executed) and a
disposable `_tool_path` per scenario. It asserts: `--help` exits 0
and lists every flag without requiring root; first `--snapshot-only`
pass on a clean DUT is `INIT`/exit 3 with a parseable JSON sidecar;
second pass (golden persisted across the separate process invocation)
is `Pass`/exit 0; a pass after deliberately corrupting the golden is
`Fail`/exit 1 with `diff_path` set; snapshot mode never makes a
systemd-related `sudo` call and never touches the real unit file;
standalone mode (no flag) does attempt the systemd-related `sudo`
call (mocked) without touching the real unit file, and does not
reboot/poweroff when the single target pass completes. 23/23
assertions pass, repeatably across multiple runs. Not yet covered:
the `Error` (exit 2) outcome, which only fires when
`collect_inventory_snapshot` itself fails to write its output file —
not safely reproducible as root without filesystem-level fault
injection (e.g. `chattr +i`), which may not be available in every
sandbox; left as follow-up.

`dev_detect.sh` automated coverage is in place; this status note will
be updated again once `dev_detect.ps1` gets an equivalent run on real
Windows hardware.

`dev_detect.ps1`: implemented (help text, `-SnapshotOnly`, INIT
detection via `Initialize-Golden`'s new `$script:_golden_was_init`,
four-state exit code, JSON sidecar). An automated harness now exists,
`src/powershell/test_dev_detect.ps1`, mirroring the bash one: it copies
the script into a temp folder per scenario (no command mocking is
needed — `dev_detect.ps1` never reboots, powers off, or installs a
scheduled task itself) and asserts `-Help`/exit 0, INIT/exit 3 on a
clean DUT, Pass/exit 0 on an unchanged second run, Fail/exit 1 after
corrupting a golden, the `mode` field (`standalone` vs `snapshot`),
`m == null`, and a 5-component sidecar.

While writing that harness, reading the code surfaced a cross-script
inconsistency: `dev_detect.ps1` emitted the sidecar `result` (and its
per-run log tag) in upper case — `PASS`/`FAIL` — whereas DET013 and the
bash side use `Pass`/`Fail`. That casing was corrected in
`dev_detect.ps1` so both scripts now satisfy the Statement's
`Pass | Fail | Error | INIT` exactly. The change is self-contained to
`dev_detect.ps1` (the other PowerShell tests use their own independent
`PASS`/`FAIL` verdicts and are unaffected).

Follow-up display cleanup after a real-run review of the NIC/storage
tables: `Gen` and `Speed` are the same fact in two notations (`Gen4` ==
`16.0 GT/s`), so `Get-PcieLinkInfo` now exposes one merged `GenSpeed`
field instead of two columns; and `ApproxGBs` was renamed
`TheoreticalGBs` to make clear it is the PCIe link's calculated
byte-throughput ceiling (Gen × Width), not a measured value and not
comparable to a NIC's Ethernet line rate — a link is routinely
provisioned well above what one port needs (e.g. a 4-port NIC card
sized for its aggregate, not per-port, throughput).

The first real Windows run (2026-06-24) surfaced a second, unrelated
defect in `function.ps1`'s `Get-PcieLinkInfo`: the NIC/storage tables
reported every PCIe link as `Gen1` with `Width`/`Speed` = `Unknown`.
Two root causes — (1) `Get-PnpDeviceProperty` returns the link
properties as `[uint32]`, but the code type-checked against `[int]`,
which is `False` for `[uint32]`, so real values silently fell back to
`0`; and (2) `DEVPKEY_PciDevice_*LinkSpeed` is an encoded enum
(`1`→2.5, `2`→5.0, `3`→8.0, `4`→16.0, `5`→32.0, `6`→64.0 GT/s), not a
raw GT/s number, so even a correctly-read value would have been
mis-scaled. The fix adds `ConvertTo-IntOrZero` (uint-safe coercion) and
`ConvertFrom-PcieSpeedCode` (enum→GT/s), guards `ConvertTo-PcieGen`
against the `0`→`Gen1` trap (now `0`→`Unknown`, plus a `Gen6` bucket),
and reads the `Max*` properties alongside `Current*` so the report
shows both current and maximum link ability (`x1 (max x4)` style). The
golden-comparison scalars are unaffected (PCIe detail lives only in the
human-readable `content_text`, never in the Pass/Fail scalar). Confirmed
against the working `CheckPCIe.ps1`, which reads the same DEVPKEYs.

The same run also surfaced a CLI-parsing defect: `dev_detect.ps1`'s
`param()` block is not an advanced function, so any argument PowerShell
could not bind (`--help`, a positional `10`, a typo) was silently
swallowed into `$args` and a normal detection pass ran anyway — bumping
the counter and writing a misleading log. (`-Help`/`-h` worked; the
Unix-style `--help` did not, which is what the operator typed.) The fix
scans `$args` after binding: `--help`/`-?`/`/?` map to help,
`--snapshot-only` maps to `-SnapshotOnly`, and anything else prints a
usage error and exits `64` (`EX_USAGE`, deliberately outside the DET013
`0/1/2/3` verdict range) before any side effect. Note this PowerShell
port still performs exactly ONE pass per invocation — the
across-reboots pass-count argument that `dev_detect.sh` accepts (`N`)
is owned here by Task Scheduler / the external orchestrator, not by the
script, and is tracked separately from this requirement.

A Layer-1 cross-OS audit (see
[`docs/contract-alignment-plan.md`](../docs/contract-alignment-plan.md))
found `dev_detect.sh`'s `--vpu-*` argument parser had the identical
silent-swallow defect: unrecognized tokens landed in `REM_ARGS` and
were never checked, so a typo'd flag ran a normal pass instead of
erroring. Fixed the same way — unrecognized tokens now print a usage
error and `exit 64`. Closing this surfaced an unrelated pre-existing
bug: `dev_detect.sh`'s EXIT trap read `_log_dir` before it is ever
assigned, so any exit occurring earlier (the new usage error, and the
pre-existing `check_api_versions` `exit 63` path) had its real exit
code silently replaced with `1` by an unbound-variable failure inside
the trap under `set -u`. Fixed by binding `_log_dir` to `""` immediately
after the trap is installed. Both bash-side fixes are covered by new
cases in `src/bash-shell/test_dev_detect.sh` (26/26 passing).

This harness has **not yet been executed** — it is queued for the
first real Windows run, which is the gate for moving the `.ps1` side
(and thus this requirement) to `verified`. That run also validates the
casing fix and the PCIe link-info fix above.
