# PWR015 — BIOS / BMC Firmware Version Reporting

## Statement

`power_cycle.py` and `reboot.py` shall record the DUT's BIOS version and BMC
(Baseboard Management Controller) firmware version on every cycle, on both
Windows and Linux DUTs, and the rendered report shall display them.

1. **BIOS version** is probed over the same SSH connection already used for
   liveness/shutdown/reboot, with an OS-specific command:
   - Linux: `sudo dmidecode -s bios-version`
   - Windows: PowerShell `(Get-CimInstance Win32_BIOS).SMBIOSBIOSVersion`
2. **BMC version** is attempted in order, stopping at the first success:
   1. **In-band**, using the OS-native IPMI tool over the same SSH session:
      - Linux: `sudo ipmitool mc info`, reading the `Firmware Revision` line.
      - Windows: `ipmiutil health`, reading the `BMC version` token.
      `ipmitool` has no clean official Windows binary, whereas `ipmiutil`
      ships a proper Windows installer — so the in-band tool differs by OS.
      Works as long as the tool and the IPMI KCS driver are installed.
   2. **Redfish** — `GET https://<bmc-host>/redfish/v1/Managers/<id>`
      against the BMC's own management IP (`--bmc-host`), reading
      `FirmwareVersion`. Independent of the DUT's OS/SSH state, since the
      BMC has its own network interface. Only attempted when `--bmc-host`
      is given.
3. A product with **no BMC** is expected to fail both methods, in which case
   `bmc_version` is reported as `"N/A"` — not an error, not a blank field.
4. Versions are collected **every cycle**, not once per session, so a
   firmware update applied mid-run (including by the test itself, on a
   firmware-soak platform) is visible in `result.json` rather than silently
   missed.

## Rationale

Endurance-test results (boot time distributions, failure rates) are only
meaningful for a fixed hardware/firmware configuration. Without recording
BIOS/BMC versions alongside the cycle data, there is no way to later confirm
"this 300-cycle run was against firmware X" or notice that a version changed
mid-run and silently split the data into two populations. BIOS and BMC are
queried by different mechanisms because they live on different management
planes: BIOS is part of the DUT's own OS-visible hardware, reachable only
through the DUT's SSH session; BMC firmware is normally exposed either
in-band (via the IPMI KCS interface the OS can see) or out-of-band (via the
BMC's own dedicated network port, independent of the DUT OS entirely). Not
every DUT has a BMC at all (e.g. desktop-class boards), so `"N/A"` is a valid
and expected steady-state value, not a failure to detect.

## Scope

`src/python/function.py` (`detect_firmware()`), `src/python/power_cycle.py`,
`src/python/reboot.py`, `src/python/config.py`, `src/python/report.py`,
`src/bash-shell/setup_dut.sh` and `src/powershell/setup_dut.ps1` (install the
in-band tools and, on Linux, grant NOPASSWD sudo for them).

## Implications

1. `--bmc-host IP`, `--bmc-user USER`, `--bmc-pass PASS` added to both
   scripts; default empty (`config.BMC_HOST/BMC_USER/BMC_PASS`). Empty
   `--bmc-host` means BMC version is only attempted via ipmitool.
2. Each cycle record in `result.json` gains `bios_version`, `bmc_version`,
   `bmc_method` (`"ipmitool"`, `"ipmiutil"`, `"redfish"`, or `null` when
   none succeeded). `null` (not collected, e.g. cycle failed before the DUT
   came alive) is distinct from `"N/A"` (collection ran but found no BMC).
3. Firmware probing only runs when `--ssh-user` or `--bmc-host` is given —
   with neither, there is no transport to probe over, so the fields stay
   `null` for the whole run.
4. `result["config"]["bmc_host"]` records the configured BMC host (or
   `null`) for traceability.
5. `report.py`'s subtitle line shows the latest recorded BIOS/BMC version
   (and BMC detection method, if any). If BIOS or BMC version differs across
   cycles within one run, a warning banner is shown — most likely a firmware
   update happened mid-test, which should not be mistaken for measurement
   noise in the boot-time statistics.
6. `dry_run=True` returns fixed placeholder values (`DRY-RUN-BIOS-1.0` /
   `DRY-RUN-BMC-1.0`) without touching the network, matching every other
   SSH/network helper in `function.py`.
7. The DUT bootstrap scripts install the in-band tools so the fields are
   populated rather than `"N/A"` on a fresh DUT:
   - `setup_dut.sh` (SET007) installs `dmidecode` + `ipmitool` and adds both
     to the test user's NOPASSWD sudoers entry (the per-cycle
     `sudo dmidecode` / `sudo ipmitool` would otherwise hang on a BatchMode
     SSH password prompt).
   - `setup_dut.ps1` (SET005) installs `ipmiutil` (winget first, then a
     direct download fallback, mirroring the existing Python install step).
     BIOS detection on Windows needs no extra tool (`Win32_BIOS` is built in).
