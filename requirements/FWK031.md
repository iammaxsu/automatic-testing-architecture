# FWK031 — DUT Self-Initialisation Before Test Execution

## Statement

Every test program that requires a live DUT shall, before its first test cycle,
bring the DUT to a **testable (alive) state** by calling the shared helper
`function.init_dut()`. A test shall not assume the DUT is already powered on,
booted, or in any particular state at invocation time.

`init_dut()` shall apply a minimal-intervention escalation chain, stopping at the
first step that leaves the DUT responding:

| Step | Condition | Action |
|------|-----------|--------|
| 1 | DUT responds to ping **OR** SSH | none — already testable |
| 2 | DUT responds to neither | GPIO power-on press, then wait up to `boot_timeout` |
| 3 | still no response | GPIO force-off → wait `off_time` → power-on, then wait up to `boot_timeout` |
| — | still no response | abort: DUT presumed dead |

When no relay/GPIO pin is available, the only remedy is to wait up to `init_wait`
seconds for a DUT that is powered but still booting (BIOS/POST); `init_wait == 0`
means fail immediately.

## Rationale

A test framework must be **robust to unknown initial DUT state**. The DUT may be:
- already up and idle (re-run, or first test in a sequence),
- powered off (a preceding `power_cycle.py` run always ends with the DUT off),
- hung (a previous test crashed the DUT).

Pushing this concern into each test — rather than into the orchestration layer
(`run_tests.sh`) or onto the operator — means:

1. **Composite test order is unconstrained.** Any test can follow any other; each
   normalises the DUT itself. There is no rule that `power_cycle.py` must run last.
2. **No operator burden.** The operator does not have to remember to leave the DUT
   in a particular state, nor pass special flags. If they forget, the test recovers.
3. **Minimal intervention.** A healthy DUT (responds to ping or SSH) is never
   disturbed. Recovery escalates from gentle (power-on press) to forceful (full
   power cycle) only as far as actually needed.

### Why GPIO, not SSH, for recovery

The init alive-check is `ping OR SSH` (`LivenessChecker.is_up()`). A DUT that
fails Step 1 responds to *neither* ping nor SSH, so an SSH-issued reboot could not
possibly reach it. Recovery is therefore purely physical (GPIO/relay). SSH is used
only by the test body, where the DUT is being *controlled*, not *revived*.

### Two liveness predicates

- **`is_up()` = ping OR SSH** — used as the Step 1 gate ("should I intervene?").
  Conservative about disturbing a working DUT.
- **`is_alive()` = ping AND SSH** — used by `wait_until_alive()` after an
  intervention ("is the DUT fully booted and ready for commands?"). Ensures SSH is
  accepting before the test hands off to its first cycle.

## Scope

`function.init_dut()` (`src/python/function.py`); `LivenessChecker.is_up()`
(`src/python/liveness.py`); every test program that consumes a live DUT
(`reboot.py` today; `disk_test`, `net_test`, `dev_detect`, `slp_test` as they are
brought into `src/`).

**`power_cycle.py` is exempt**: it *produces* DUT state rather than *requiring* it.
Its first cycle powers the DUT on as a normal step, and its warmup cycle (PWR009)
already absorbs unknown initial state. A "testable state" for power_cycle is simply
a working relay, not a live DUT.

## Implications

1. `init_dut()` returns `(ok, method)`; `method` records which escalation step
   resolved the state (`already-up`, `power-on`, `power-cycle`, `wait`) or how it
   failed (`no-relay`, `failed-wait`, `dead`). Tests log this and abort on `ok=False`.
2. Recovery reuses existing config values: `GPIO_PIN`, `POWER_TYPE`,
   `ATX_SHORT_PRESS_SEC`, `ATX_LONG_PRESS_SEC`, `OFF_TIME_SEC`, `BOOT_TIMEOUT_SEC`.
   No init-specific GPIO pin is introduced (`--pin` defaults to `config.GPIO_PIN`).
3. `init_dut()` is skipped when resuming an interrupted session (state already
   established) and in `--dry-run` (returns `("dry-run")` without touching hardware).
4. All test programs expose a common `--ssh-user` argument (FWK-wide); init does not
   use it, but the test body and OS-detection may.
5. Each test forwards GPIO arguments (`--pin`, `--type`) via the shared
   `COMMON_ARGS` in `run_tests.sh`, so a single invocation configures recovery for
   every phase.
