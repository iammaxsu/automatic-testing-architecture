# FWK032 — In-Test DUT User Notification

## Statement

Every test program that executes on or controls a DUT shall display an
ongoing, human-readable notification on the DUT's interactive desktop or
console during the test. The notification shall:

1. **Appear after each boot** (or at the start of the test for programmes
   that do not reboot the DUT), not only at shutdown/reboot time.
2. **Identify the test and progress** — at minimum: test name and current
   cycle count (e.g. `"Power cycle test in progress — cycle 3 / 10.
   Do not use."`).
3. **Fail silently** — a delivery failure (no logged-in user, notification
   service unavailable, insufficient privileges) shall not abort the test
   or affect the verdict.

### Per-platform mechanism

| Platform | Mechanism |
|----------|-----------|
| Pi-controlled Windows DUT (`power_cycle.py`, `reboot.py`) | SSH `msg * <text>` via `function.notify_dut()`, called after `wait_until_alive()` returns True each cycle |
| Pi-controlled Linux DUT (`power_cycle.py`, `reboot.py`) | SSH `wall <text>` via `function.notify_dut(..., dut_os="linux")`, called after `wait_until_alive()` returns True each cycle |
| DUT-local Windows (`reboot.ps1`) | `msg.exe *` via `Notify-User` helper, called after each cycle's boot is recorded |
| DUT-local Linux (Bash — `disk_test.sh`, `net_test.sh`, etc.) | `wall` broadcast via `test_warning_daemon.sh`, refreshed each soak phase |

## Rationale

Hardware tests run unattended for hours. If an operator or bystander
inadvertently interacts with the DUT (keyboard input, mouse, powering it
off) during a test, the result is corrupted. A persistent, visible reminder
that the machine is under test reduces this risk without requiring physical
barriers or labels.

The existing `msg.exe` / `wall` mechanisms in the DUT-local scripts show this
is already understood as necessary; FWK032 formalises the rule so that every
future test program implements it consistently.

## Scope

All test programs in `src/`: `power_cycle.py`, `reboot.py` (Pi-side Python);
`reboot.ps1` (DUT-local PowerShell); `disk_test.sh`, `net_test.sh`,
`dev_detect.sh`, `slp_test.sh` (DUT-local Bash Shell).

## Implications

1. **Pi-side Python tests**: `function.notify_dut()` must run after
   `wait_until_alive()` in each cycle, and is dispatched by `dut_os`
   (resolved from `--dut-os auto|windows|linux` via `detect_dut_os()`):
   - `dut_os="windows"` polls `query session` to confirm an Active desktop
     session exists before sending `msg *`, handling the race where `sshd`
     becomes ready before the interactive logon completes.
   - `dut_os="linux"` polls SSH readiness with a no-op command, then
     broadcasts with `wall <text>` — `wall` needs no active login session, so
     no session-detection step is required.
   `power_cycle.py` fires the notification in a background thread (ON_TIME
   provides ≥ 90 s buffer); `reboot.py` joins the thread (30 s timeout)
   before issuing the next reboot command.
2. **DUT-local PowerShell**: `Notify-User` in `reboot.ps1` already satisfies
   this requirement (PWR011); no change needed.
3. **DUT-local Bash**: `test_warning_daemon.sh` and `wall` satisfy this for
   Linux DUTs. BUG0007 and BUG0022 document current deficiencies (stale
   message text, infrequent refresh) that must be resolved.
4. The notification text shall include enough context for someone unfamiliar
   with the test framework to understand what is happening and that they
   should not interact with the machine.

## Verification

For each test program:
- Run a short test (2–3 cycles) while an interactive user is logged in to the
  DUT.
- Confirm that a notification appears on the DUT desktop **after each boot**
  (not only at shutdown) and that the cycle count is correct.
- Confirm that when no user is logged in, the test completes normally with no
  error related to the notification.
