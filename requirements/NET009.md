# NET009 — Minimum Throughput Thresholds

## Statement

The framework shall enforce a minimum TCP throughput threshold, expressed as a
percentage of the speed under test (NET004), and declare a per-(interface,
speed, combination) verdict per NET008:

- TCP (forward and reverse): throughput ≥ threshold% of the speed under test →
  PASS; below threshold → FAIL; iperf3 returned no data → UNKNOWN.
- UDP: threshold TBD; not yet implemented.

The threshold percentage is **per-speed-tier**, not a single global value:
TCP/IP framing and protocol overhead consume a proportionally larger share of
the link at lower speeds, so a flat 95% is unrealistic for e.g. 100 Mbps links
(measured throughput of ~94-95% of nominal is normal and correct at 100M).
Configuration shall provide:

- a default percentage applied to any speed not otherwise listed, and
- a per-speed-tier table mapping `speedMbps:pct` pairs (e.g. "10:90,100:90,
  1000:95,2500:95,5000:95,10000:95") that overrides the default for the
  listed speeds.

A single global override (e.g. a command-line flag) may be supplied to apply
one flat percentage to every speed, bypassing the per-tier table entirely —
this is for diagnostic/manual runs, not normal operation.

The threshold percentage and the resulting threshold (in Mbps) actually
applied to each (interface, speed) combination shall be recorded in
result.json and shown in the rendered report (NET008's `reason` field and
FWK028), so the operator can see which threshold applied and why a given
speed passed or failed against it.

## Rationale

Without thresholds, the test can never automatically fail on degraded
hardware. A single global percentage either over-fails low-speed links (95%
of 100M is rarely achievable due to overhead) or under-tests high-speed links
(too lenient at 1000M+), so the threshold must vary by speed tier — and that
variation must be visible to the operator, not a silent magic number.

## Scope

All scripts and shared libraries in the framework.

## Implications

1. The per-speed-tier threshold table and default percentage are configurable
   (SET001), not hardcoded.
2. Each reported (interface, speed) item records the percentage and the
   resulting Mbps threshold that was actually applied.
3. The rendered report explains the threshold used for each speed, per NET008.
4. Non-compliance must be corrected before merge.
