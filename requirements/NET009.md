# NET009 — Minimum Throughput Thresholds

## Statement

A speed's TCP throughput shall be judged against a percentage of the
**achievable goodput** of the link, not against a percentage of its nominal
line rate:

```
threshold = link_speed × efficiency(MTU) × pct / 100

efficiency(MTU) = (MTU − l3l4_overhead) / (MTU + frame_overhead)
```

with `frame_overhead = 38` bytes (preamble+SFD 8, Ethernet header 14, FCS 4,
inter-frame gap 12) and `l3l4_overhead = 52` bytes (IP 20 + TCP 20 +
timestamps 12). Both directions shall meet the threshold.

`pct` shall default to **95** and shall be **uniform across every link speed**.

The measurement method shall use enough parallel TCP streams that the host is
not the limiting factor: **one stream below 25 Gb/s, eight at or above it**.

Every artefact shall record the rule that produced its verdicts —
formula, MTU, both overhead figures, the resulting efficiency, `pct`, any
per-speed overrides, the stream count, and whether UDP loss or NIC error
counters gate the verdict — in `result.json`, from which the report renders it.

## Rationale

The frame-by-frame accounting behind these figures, the per-MTU ceiling table
and the argument for why a payload measurement can still judge hardware are set
out in [`docs/ethernet-goodput-ceiling.md`](../docs/ethernet-goodput-ceiling.md).
That note explains this requirement; this requirement is the normative rule.

### Why not a percentage of line rate

iperf3 reports **TCP payload**; the link speed is **wire rate**. Everything
between them is unavoidable and invisible to goodput:

| Per frame | Bytes |
|---|---|
| Preamble + SFD | 8 |
| Ethernet header | 14 |
| FCS | 4 |
| Inter-frame gap | 12 |
| IP header | 20 |
| TCP header | 20 |
| TCP timestamps (Linux default) | 12 |

At MTU 1500 a frame spends 1538 bytes of wire carrying 1448 bytes of payload:

```
1448 / 1538 = 94.15 %
```

**94.15 % is the ceiling.** The previous rule asked for 95 % of line rate,
which is above it — unreachable at every speed from 10 Mb/s to 800 Gb/s
(BUG0061).

The empirical value the old threshold came from is the same number seen from
the other side. Gigabit NICs were observed reaching "940 Mb/s and above", and
940 Mb/s **is** 94.0 % — sitting on the ceiling, not exceeding 95 %. The
observation was correct; the threshold written from it was one percentage point
above what had actually been measured, and that gap was small enough at 1 Gb/s
to look like measurement noise. At 100 Gb/s the same gap is 800 Mb/s and the
error became visible.

### Why one percentage suffices for every speed

`efficiency(MTU)` contains no speed term. The framing cost is the same fraction
at 10 Mb/s and at 800 Gb/s, so once it is modelled explicitly there is nothing
left for a per-speed table to correct.

The previous tier table (`10:90, 100:90, 1000:95, …`) was hand-compensating for
exactly this unmodelled overhead. It is now empty by default. The mechanism is
retained for a different purpose: recording a **measured platform limit**, such
as a host whose PCIe generation cannot carry 400 Gb/s. Such an entry is a fact
about the bench, not about the NIC, and must be justified where it is set.

### Why the stream count is part of the standard

A single TCP stream is bounded by one CPU core's ability to drive the stack. On
the reference DUT it plateaued at 75–85 Gbit/s **regardless of link speed**, so
100 G and 200 G both measured about 80 Gbit/s — a number describing the host,
not the NIC.

With eight streams the same hardware reached 99.8 %, 100.1 % and 100.1 % of
achievable at 25 G, 50 G and 100 G. The stream count therefore is not a tuning
preference; below 25 G it changes nothing, and above it, the wrong choice makes
the test measure the wrong device.

### Why MTU is part of the standard

| MTU | Ceiling |
|---|---|
| 1500 | 94.15 % |
| 4000 | 97.77 % |
| 9000 | 99.00 % |

The same 38 bytes of framing amortised over six times the payload. This is also
why NET018's jumbo verification matters beyond "does 9000 work": at MTU 9000 the
ceiling is 99 %, so a measurement of 96 % is a real deficit, whereas at MTU 1500
a measurement of 94 % is perfection. The MTU the throughput runs use is recorded
so a report cannot be compared against one taken at a different MTU without the
difference being visible.

### Why the derivation must travel with the numbers

A verdict is auditable only if the rule that produced it is recoverable from the
same artefact. "Why did 94.2 Gbit/s fail on a 100 G link?" is unanswerable from
a report that records only the verdict — the reader would need to know which
framework version ran, at what MTU, with how many streams, and which formula was
current at the time.

This is FWK028 applied to the standard itself, not just to the measurements. It
cost this project one wrong requirement and several hours of bench time before
the discrepancy was noticed at all.

## Scope

| Applies to | Notes |
|---|---|
| `net_test.sh` | `_goodput_efficiency`, `_iperf_parallel_for`, `_tcp_pass_pct_for` |
| `config.sh` | the overhead, MTU, pct, tier and stream settings |
| `function.sh` | renders the method section of the report from `result.json` |
| `net_test.ps1` | FWK036 parity — pending |

Applies to TCP verdicts. UDP is offered at full link rate with no flow control,
so its loss is an expected outcome of the method and is reported rather than
judged unless explicitly gated (NET017).

## Implications

1. `pct` is a share of **achievable** goodput. `95` no longer means "95 % of the
   link speed" and reports from before this change are not comparable.
2. The tier table is empty by default. An entry is a claim about the bench, and
   the reason belongs in the commit that adds it.
3. Speeds validated against this rule, MTU 1500, `pct` 95:

   | Link | Ceiling | Threshold |
   |---|---|---|
   | 10 M | 9.4 | 8.9 |
   | 100 M | 94.1 | 89.4 |
   | 1000 M | 941.5 | 894.4 |
   | 2500 M | 2353.7 | 2236.0 |
   | 5000 M | 4707.4 | 4472.0 |
   | 10 G | 9414.8 | 8944.1 |
   | 25 G | 23537 | 22360 |
   | 40 G | 37659 | 35776 |
   | 50 G | 47074 | 44720 |
   | 100 G | 94148 | 89441 |
   | 200 G | 188297 | 178882 |
   | 400 G | 376593 | 357763 |
   | 800 G | 753186 | 715527 |

4. `l3l4_overhead` assumes Linux's default TCP timestamps. A DUT with
   `tcp_timestamps=0` has a 94.93 % ceiling; the figure is configurable and is
   recorded per run.
5. A measurement slightly **above** the computed ceiling is expected on NICs
   doing TSO/GRO and is not an error — the model is deliberately conservative.

## Verification

`src/bash-shell/test_net_threshold.sh` — the MTU 1500 ceiling is 0.9415 and the
MTU 9000 ceiling is 0.9900; an MTU below the header size degrades safely; the
four measurements from session `20260812T132556` all pass; **the previous
formula is shown to have failed all four**, so the change is demonstrably not
cosmetic; genuinely slow links still fail; and the threshold never exceeds the
ceiling at any speed from 1 G to 400 G.

`src/bash-shell/test_net_method_record.sh` — `result.json` carries the
requirement id, formula, MTU, both overheads, the efficiency, `pct`, the tier
string, the stream policy and both gating flags; the report's method section is
rendered from that record rather than hand-written; and the stream policy
resolves to 1 below 25 G and 8 at or above.
