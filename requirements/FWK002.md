# FWK002 — Cross-Language Naming Conventions

## Statement

All scripts and shared libraries shall follow the naming rules in the table
below, by language. The unifying rule across all three languages is:
**`_` prefix marks internal / not-for-external-callers identifiers.**
Everything else maps to each language's established industry standard.

### Python (PEP 8)

| Role | Convention | Example |
|------|-----------|---------|
| Module-level public constant (user-configurable) | `UPPER_SNAKE_CASE` | `BOOT_TIMEOUT_SEC = 120` |
| Module-level private variable | `_lower_snake_case` | `_COUNTER_FILE = "counter.log"` |
| Local variable inside a function | `lower_snake_case` | `boot_time = 0.0` |
| Public function / method | `lower_snake_case` | `def run_one_cycle():` |
| Private / internal function | `_lower_snake_case` | `def _force_off():` |
| Class name | `PascalCase` | `class ShutdownCoordinator:` |

### Bash

| Role | Convention | Example |
|------|-----------|---------|
| Exported / environment constant | `UPPER_SNAKE_CASE` | `export BOOT_TIMEOUT=120` |
| Script-level private variable | `_lower_snake_case` | `_entry_dir=$(cd ...)` |
| Local variable inside a function (`local`) | `lower_snake_case` | `local count=0` |
| Function | `lower_snake_case` | `run_cycle() { ... }` |

### PowerShell

| Role | Convention | Example |
|------|-----------|---------|
| Script-level variable (shared within the script) | `$_camelCase` | `$_logPath`, `$_date2` |
| Local variable inside a function | `$camelCase` (no `_`) | `$goldenPath`, `$currentText` |
| Function name | `Verb-Noun`; verb from approved list; noun is `PascalCase` with no hyphens | `Initialize-Golden`, `Get-CpuText` |

**PowerShell notes:**
- `$_` alone is the automatic variable `$PSItem` (current pipeline object); only use
  `_` as a name *prefix* on longer names (e.g. `$_logPath`), never the bare `$_`.
- Approved verbs are those returned by `Get-Verb`. The following are explicitly
  disallowed because PS does not recognise them: `Parse`, `Ascend`, `Approx`,
  `TryGet`, `Ensure`, `Append`. Correct replacements:

  | Non-standard | Approved replacement |
  |-------------|---------------------|
  | `Parse-X`   | `ConvertTo-X` or `Get-X` |
  | `Ascend-X`  | `Resolve-X` |
  | `Approx-X`  | `Get-X` |
  | `TryGet-X`  | `Get-X` (handle absence in the body) |
  | `Ensure-X`  | `Initialize-X` |
  | `Append-X`  | `Add-X` |

- Noun must not contain hyphens: `Get-Cpu-Text` is wrong; `Get-CpuText` is correct.

## Rationale

Using `_` prefix to signal internal identifiers achieves three goals:

1. **Visual recognition** — any reader immediately distinguishes "this is
   internal" from "this is a public constant or parameter" without consulting
   documentation. A developer unfamiliar with the codebase can orient themselves
   in seconds.
2. **Tooling alignment** — Python's `from module import *` skips `_`-prefixed
   names; Bash `local` scoping is reinforced by the prefix; PowerShell's
   `PSScriptAnalyzer` enforces approved verbs via the `PSUseApprovedVerbs` rule.
3. **Cross-language consistency** — a developer working across all three
   languages only needs to remember one rule: `_` means private/internal.
   The remaining conventions map to each language's own PEP/standard,
   minimising conflicts with community tooling and established practices.

For PowerShell local variables, function scope already enforces privacy, so
adding `_` prefix inside function bodies is redundant and misleading — it
would imply "script-level state" when the variable is in fact local.

## Scope

All scripts and shared libraries: `src/bash-shell/`, `src/powershell/`,
`src/python/`.

## Implications

- Non-compliance must be corrected before merge.
- Python public constants (such as those in `config.py`) use `UPPER_CASE`,
  not `_` prefix — adding `_` to a public constant would break `import *`
  and confuse any reader expecting "private implementation detail."
- PowerShell function names must use verbs from the approved list; run
  `Get-Verb | Select-Object -ExpandProperty Verb` to check a verb.
- PowerShell local variables inside functions use `$camelCase` (no `_`);
  only script-scope variables use `$_camelCase`.
- Renaming an existing function is a breaking change; all call sites must
  be updated in the same commit.

## Verification

Code Review: verify all committed scripts follow the per-language table;
verify no PowerShell function uses an unapproved verb (run
`Invoke-ScriptAnalyzer -Path <file> -IncludeRule PSUseApprovedVerbs`).
