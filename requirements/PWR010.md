# PWR010 — Cycle Phase Timing Model and Parameter Defaults

## Statement

One power cycle (loop) shall consist of exactly four phases, executed in order. Two phases are **variable** (they end as soon as the DUT changes state, capped by a timeout) and two are **fixed** waits:

| # | Phase | Type | Parameter | CLI flag | Default | Ends when… |
|---|-------|------|-----------|----------|---------|------------|
| 1 | BOOT | variable, capped | `BOOT_TIMEOUT_SEC` | `--boot-timeout` | 120 s | DUT answers ping **and** SSH; timeout → `NO_BOOT` |
| 2 | ON_TIME | fixed | `ON_TIME_SEC` | `--on` | 90 s | full duration elapses; drop-off → `CRASH` |
| 3 | SHUTDOWN | variable, capped | `DEAD_TIMEOUT_SEC` | (config only) | 30 s | DUT goes offline; timeout → force-off + `HANG_SHUTDOWN` |
| 4 | OFF_TIME | fixed | `OFF_TIME_SEC` | `--off` | 60 s | full duration elapses |

Therefore one cycle ≈ *(actual boot time)* + `ON_TIME_SEC` + *(actual shutdown time)* + `OFF_TIME_SEC`. The BOOT and SHUTDOWN timeouts are **upper limits, not fixed waits**: a DUT that boots in 45 s spends 45 s (not 120 s) in phase 1.

Each timing parameter shall have a default in `config.py` with an inline comment stating its meaning, its CLI flag, and its rationale. Every parameter shall be overridable at run time via its CLI flag, and `--help` shall list all flags with their effective defaults.

## Rationale

Operators reason about test duration in terms of "one loop = on-time + off-time", but the implementation has four phases with different semantics. Documenting the model removes two recurring misconceptions:

1. **BOOT and ON_TIME are sequential, not parallel.** `ON_TIME_SEC` is counted from the moment boot is confirmed, not from the power-button press. Total on-state time is *boot time + ON_TIME*, not `max(boot, ON_TIME)`.
2. **A timeout is a ceiling, not a dwell.** The DUT being alive ends phase 1 immediately; only a DUT that never appears consumes the full `BOOT_TIMEOUT_SEC`.

Default values reflect the intended operator experience for an Ubuntu/Windows DUT:

- **`BOOT_TIMEOUT_SEC = 120`** — a healthy DUT should reach the desktop and accept ping+SSH within ~120 s. A slower boot is deliberately classified as `NO_BOOT` (a quality defect), not silently tolerated.
- **`ON_TIME_SEC = 90`** — long enough to run a `dev_detect` pass and to give the operator a window to abort the run before the next power-off, while keeping a 1000-cycle test to a practical wall-clock duration.
- **`OFF_TIME_SEC = 60`** — settle time ensuring the PSU and DUT fully de-energise between cycles.
- **`DEAD_TIMEOUT_SEC = 30`** — generous margin for a clean OS shutdown before force-off is judged necessary.

## Scope

`src/python/config.py`, `src/python/power_cycle.py`.

## Implications

- The shutdown phase (3) is delegated to `ShutdownCoordinator` (see PWR009): with `--ssh-user` the OS shuts itself down via SSH and the power button is used only to power on; without it, an ATX button press powers off.
- `ON_TIME_SEC` is the only window in which `CRASH` (post-boot instability) can be detected; setting it very low trades test speed for reduced stability coverage.
- Worked example (DUT boots in ~60 s, shuts down in ~15 s):
  `60 + 90 + 15 + 60 = 225 s ≈ 3.75 min/cycle`; 1000 cycles ≈ 2.5 days.
- Changing a default in `config.py` does not require touching `power_cycle.py`: the CLI defaults are read from `config.py` and surfaced through `--help` via `%(default)s`.
