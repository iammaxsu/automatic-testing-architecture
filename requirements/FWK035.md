# FWK035 — Standard SSH Options for DUT Connections

## Statement

Every control-node (Pi-side) process that opens an SSH connection to a DUT shall
build its `ssh` command line from a single shared option set, exposed as
`function.ssh_base_opts(connect_timeout)`. No call site shall hand-assemble its
own `-o` option list. The shared option set shall include:

| Option | Value | Purpose |
|--------|-------|---------|
| `StrictHostKeyChecking` | `no` | accept an **unknown** host without prompting |
| `UserKnownHostsFile` | `/dev/null` | never read or persist a host key, so a host whose key has **changed** is also accepted |
| `LogLevel` | `ERROR` | suppress the multi-line "host identification has changed" warning banner |
| `BatchMode` | `yes` | never fall back to an interactive password prompt |
| `ConnectTimeout` | caller-supplied | bound the connect attempt |

Non-Python control-node scripts that cannot import `function` (e.g.
`stop_tests.sh`) shall reproduce the same option set inline, with a comment
referencing this requirement so the two stay in sync.

## Rationale

`StrictHostKeyChecking=no` alone is a common but incomplete idiom. It silences the
prompt only for a **first-contact, unknown** host; it does **not** override
OpenSSH's hard refusal when a `known_hosts` entry already exists and the host's
current key no longer matches it. That "changed key" case is exactly what a
hardware test lab produces routinely: DUTs are reimaged, OpenSSH is reinstalled,
or the same IP is reused for a different machine (or a different OS), so the host
key legitimately changes. When that happens, OpenSSH aborts the connection with a
loud "REMOTE HOST IDENTIFICATION HAS CHANGED!" banner and a non-zero exit, and
**every** SSH-driven test cycle fails even though the DUT is up and reachable
(BUG0033 — observed as 100 % `SSH_ERROR` on a DUT that `init_dut()` had just
powered on and confirmed alive).

In a physically controlled lab the host-key trust check provides no real
protection — there is no meaningful man-in-the-middle threat between the control
node and a DUT on the bench — so discarding host-key state with
`UserKnownHostsFile=/dev/null` is the correct trade-off. `LogLevel=ERROR` keeps
the (now harmless) churn out of the test logs.

Centralising the option set (rather than repeating it at each call site) is itself
a requirement, not a convenience: the bug existed because six independent call
sites each carried their own copy of the list and a needed option was absent from
all of them. One source of truth makes the option set impossible to get
inconsistently wrong, in the same spirit as FWK028's canonical-form rule.

## Scope

All control-node SSH invocations:

| Call site | File |
|-----------|------|
| `detect_dut_os()` | `src/python/function.py` |
| `restore_dut_env()` | `src/python/function.py` |
| `notify_dut()` worker | `src/python/function.py` |
| `_ssh_reboot()` | `src/python/reboot.py` |
| `Shutdowner._try_ssh()` | `src/python/shutdown.py` |
| `_ssh_run()` | `src/python/sleep_test.py` |
| DUT-side stop (inline) | `src/python/stop_tests.sh` |

Out of scope: DUT-local scripts that do not originate SSH connections, and the
`scp`/key-distribution performed once by `setup_dut.*` (SET007), which is an
operator-supervised first-contact step.

## Implications

1. `function.ssh_base_opts(connect_timeout)` returns the `-o …` list that sits
   between the `ssh` executable and the `user@host` target; call sites splat it:
   `["ssh", *function.ssh_base_opts(t), "-p", str(port), f"{user}@{host}", cmd]`.
2. `LogLevel=ERROR` affects only `ssh`'s own diagnostics, not the remote command's
   stdout, so probes that parse output (`detect_dut_os()` reading `uname -s`,
   `notify_dut()` reading `query session`) are unaffected.
3. `shutdown.py` imports `function` solely to reach this helper; this introduces no
   cycle (`function` imports only `config`).
4. A host whose key has changed now connects silently instead of failing, so the
   `rc == 255` "connection closed by remote (reboot initiated)" success path in
   `_ssh_reboot()` is reached for the intended reason (the OS tearing down the link)
   rather than being masked by a key-verification refusal.

## Verification

Code Review:
- Confirm `function.ssh_base_opts()` exists and returns all five options above.
- Confirm every call site in the Scope table builds its `ssh` command via the
  helper (or, for `stop_tests.sh`, an inline copy with a back-reference comment),
  and that no residual hand-rolled `StrictHostKeyChecking=no`-only list remains.

Field check: against a DUT whose key has changed since it was last contacted
(e.g. reimaged), confirm a reboot/shutdown/sleep cycle now connects and succeeds
instead of failing with "REMOTE HOST IDENTIFICATION HAS CHANGED".
