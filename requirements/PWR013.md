# PWR013 — Reboot Test Initial State Normalisation

## Statement

`reboot.py` shall include an init phase that normalises the DUT to a known
SSH-reachable state before the first test cycle begins.  The init phase handles
three situations, resolved in priority order:

### Situation 1 — DUT already online
If the DUT responds to the liveness check at startup, the init phase completes
immediately and the first test cycle begins without any delay.

### Situation 2 — DUT offline; GPIO power-on requested (`--pin N`)
If the DUT is offline **and** a GPIO pin is specified (`--pin N`), `reboot.py`
shall:
1. Issue one power-on signal using the relay (ATX short press or AT relay close,
   selected by `--type`).
2. Wait up to `--boot-timeout` seconds for the DUT to become SSH-reachable.
3. Proceed to the first test cycle if the DUT comes online; abort with a
   diagnostic if the boot timeout expires.

This situation applies to the composite test scenario where `power_cycle.py`
(which always ends with the DUT powered **off**) runs immediately before
`reboot.py`. The operator passes the same `--pin` and `--type` to both scripts;
`run_tests.sh` forwards these arguments to both phases automatically.

### Situation 3 — DUT physically on but SSH not ready (`--init-wait N`)
If the DUT is offline **and** `--init-wait N` is set, `reboot.py` shall poll
for SSH connectivity for up to N seconds.  This handles the case where the DUT
is already powered on but has not yet completed booting (BIOS/POST, slow OS
initialisation).

If the DUT does not become reachable within N seconds, the test aborts with a
diagnostic.

### No remedy configured
If the DUT is offline and neither `--pin` nor a positive `--init-wait` is
provided, `reboot.py` shall abort immediately with a clear diagnostic message
listing the available remedies.

## Rationale

`power_cycle.py` always ends with the DUT powered **off** — this is correct and
intentional (PWR009, PWR010).  Without an init phase, `reboot.py` would fail
immediately in any composite test scenario because its first cycle requires
SSH access.

Placing the init logic in `reboot.py` rather than in `run_tests.sh` keeps the
behaviour self-contained and reusable: `reboot.py` can be invoked standalone
after power_cycle with no wrapper script, and the init parameters are visible
in the standard `--help` output.

Using the same `--pin` / `--type` arguments as `power_cycle.py` avoids
introducing a parallel GPIO configuration vocabulary.

## Scope

`src/python/reboot.py`; `src/python/config.py` (new constants `INIT_GPIO_PIN`,
`INIT_WAIT_SEC`); `src/python/run_tests.sh` (forwards `--pin` and `--type` to
both phases via `COMMON_ARGS`).

## Implications

1. `reboot.py` imports `RelayController` from `relay.py` only for the init phase;
   no GPIO is used during normal test cycles (those are pure SSH).
2. `config.py` provides `INIT_GPIO_PIN = None` (default: GPIO init disabled) and
   `INIT_WAIT_SEC = 0` (default: fail immediately if offline).
3. `run_tests.sh` passes `--pin` and `--type` in `COMMON_ARGS` so they are
   forwarded to both `power_cycle.py` and `reboot.py`.  The `--leave-on` flag
   is removed from `run_tests.sh`; the GPIO init mechanism in `reboot.py`
   makes it unnecessary.
4. The init phase is skipped when `--no-check` is set or when resuming a
   previously interrupted session (the DUT state is assumed correct).
5. The init phase is fully exercised by `--dry-run` (GPIO and liveness calls
   are simulated).

## Verification

Code Review:
- Confirm `reboot.py` handles all three situations and the no-remedy case.
- Confirm `run_tests.sh` passes `--pin` and `--type` in `COMMON_ARGS`.
- Confirm `config.py` documents `INIT_GPIO_PIN` and `INIT_WAIT_SEC` with
  `# CLI:` comments.

Manual test (composite):
1. Run `power_cycle.py --cycles 3 ...` — DUT ends powered off.
2. Run `reboot.py --cycles 3 --pin N --type ATX ...` — verify DUT is powered on
   by the init phase, then 3 reboot cycles complete normally.
