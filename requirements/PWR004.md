# PWR004 — Per-Cycle Verdict Taxonomy

## Statement

Each boot cycle shall be assigned exactly one of the following verdicts:

| Verdict | Condition |
|---------|-----------|
| `PASS` | DUT came online within `BOOT_TIMEOUT`, remained alive for the full `ON_TIME`, and stopped responding within `DEAD_TIMEOUT` after power-off. |
| `NO_BOOT` | DUT did not respond to ping and TCP within `BOOT_TIMEOUT` after power-on. |
| `CRASH` | DUT was alive but stopped responding during the `ON_TIME` health-check interval. |
| `HANG_SHUTDOWN` | DUT continued to respond to ping beyond `DEAD_TIMEOUT` after power-off; force-off was applied automatically. |
| `RELAY_ERROR` | GPIO relay operation raised an exception during power-on or power-off. |

The verdict shall be recorded in the per-cycle JSON record and used to compute the overall test verdict.

## Rationale

A binary pass/fail without sub-categories provides insufficient diagnostic information. Distinguishing `NO_BOOT` from `CRASH` from `HANG_SHUTDOWN` allows operators to identify whether the failure is a boot issue, a runtime stability issue, or a shutdown issue without reading raw logs.

## Scope

`src/python/power_cycle.py`.

## Implications

- Liveness checking must be enabled to differentiate `NO_BOOT`, `CRASH`, and `HANG_SHUTDOWN`; with `--no-check`, the test can only detect `RELAY_ERROR`.
- `HANG_SHUTDOWN` triggers an automatic ATX long-press or AT relay open to ensure the DUT is powered off before the next cycle.

## Verification

Code Review: confirm each verdict is assigned under exactly the conditions specified; confirm `HANG_SHUTDOWN` triggers force-off.
