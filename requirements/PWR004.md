# PWR004 — Per-Cycle Verdict Taxonomy

## Statement

Each boot cycle shall be assigned exactly one of the following verdicts:

| Verdict | Condition |
|---------|-----------|
| `PASS` | DUT came online within `BOOT_TIMEOUT`, remained alive for the full `ON_TIME`, and stopped responding within `DEAD_TIMEOUT` after power-off. |
| `NO_BOOT` | DUT did not respond to ping and TCP within `BOOT_TIMEOUT` after power-on. |
| `CRASH` | DUT was alive but stopped responding during the `ON_TIME` health-check interval. |
| `HANG_SHUTDOWN` | DUT continued to respond to ping beyond `DEAD_TIMEOUT` after power-off; force-off was applied automatically. |
| `RELAY_ERROR` | GPIO relay operation raised an exception during power-on or power-off. |

The verdict shall be recorded in the per-cycle JSON record and used to compute the overall test verdict.

### `NO_BOOT` sub-classification

A `NO_BOOT` cycle shall additionally record a `no_boot_kind` distinguishing two
physically different failures, derived from whether the DUT responded to ping at
any point during the boot wait (`liveness.wait_until_alive` tracks this):

| `no_boot_kind` | Condition | Meaning |
|----------------|-----------|---------|
| `slow_boot` | DUT responded to ping during the wait, but SSH/TCP was not ready before `boot_timeout` | The DUT was booting, just too slowly — the timeout was too tight (see PWR016 adaptive raising). |
| `no_power_on` | DUT never responded to ping for the entire `boot_timeout` | The DUT most likely did not power on at all (power-button press / relay / DUT power-state issue) — raising the timeout will not help. |

The per-cycle `notes` shall state which case occurred, and the HTML report shall
surface a warning banner listing any `no_power_on` cycles so the operator does
not mistake a failed power-on for a boot-time timeout. This applies to both
`power_cycle.py` and `reboot.py` (FWK036); for `reboot.py`, `no_power_on` means
the DUT never came back after the SSH reboot command.

## Rationale

A binary pass/fail without sub-categories provides insufficient diagnostic information. Distinguishing `NO_BOOT` from `CRASH` from `HANG_SHUTDOWN` allows operators to identify whether the failure is a boot issue, a runtime stability issue, or a shutdown issue without reading raw logs.

## Scope

`src/python/power_cycle.py` (full taxonomy); `src/python/reboot.py` and
`src/python/liveness.py` for the `PASS` / `NO_BOOT` (`slow_boot` / `no_power_on`)
subset that applies to the reboot test.

## Implications

- Liveness checking must be enabled to differentiate `NO_BOOT`, `CRASH`, and `HANG_SHUTDOWN`; with `--no-check`, the test can only detect `RELAY_ERROR`.
- `HANG_SHUTDOWN` triggers an automatic ATX long-press or AT relay open to ensure the DUT is powered off before the next cycle.
- The `NO_BOOT` sub-classification requires liveness (ping) tracking during the
  boot wait; with `--no-check` it cannot be determined.

## Verification

Code Review: confirm each verdict is assigned under exactly the conditions specified; confirm `HANG_SHUTDOWN` triggers force-off; confirm `NO_BOOT` records `no_boot_kind` (`slow_boot` vs `no_power_on`) from the ping-seen-during-wait signal, and that the report banners the `no_power_on` cycles.
