# FWK037 — System Configuration Inventory in Every Test

## Statement

Every test shall record and display a **system configuration inventory** — a
best-effort snapshot of the DUT's hardware/firmware/OS configuration under which
the test ran — so an operator can tell *what was being tested* even though the
configuration itself does not affect the pass/fail result.

The inventory shall be produced by a single shared helper (`collect_system_info`
in `function.sh` / `function.py` / `function.ps1`, FWK036 parity) and shall
include at least, when the underlying tool is available:

| Field | Linux source | Windows source |
|-------|--------------|----------------|
| Hostname | `hostname` | `$env:COMPUTERNAME` |
| OS name + version | `/etc/os-release`, `uname -r` | `Get-CimInstance Win32_OperatingSystem` |
| Board / product / serial | `dmidecode -t system/baseboard` | `Win32_BaseBoard` / `Win32_ComputerSystemProduct` |
| BIOS / BMC version | `dmidecode -s bios-version`, `ipmitool`/Redfish (existing firmware reporting) | `Win32_BIOS`, `ipmiutil`/Redfish |
| CPU model, socket / core / thread count | `lscpu`, `/proc/cpuinfo` | `Win32_Processor` |
| RAM: usable total, installed total, DIMM population | `/proc/meminfo`, `dmidecode -t memory` (see DET002) | `Win32_ComputerSystem`, `Win32_PhysicalMemory` |

The inventory shall be:

1. **Written to `result.json`** under a top-level `system_info` object
   (canonical, FWK028), and
2. **Rendered in the HTML report** (header or a dedicated "System configuration"
   section), and
3. **Best-effort / non-fatal** — a missing tool or unreadable field is recorded
   as `unknown` / `N/A` and never aborts or fails the test (mirrors FWK032).

This is **informational context**, distinct from the DET hardware-presence tests
(DET001–DET004), which assign pass/fail. The two may share detection code, but
the inventory itself never changes a verdict.

## Rationale

DUTs are frequently reconfigured between runs — CPUs and DIMMs are swapped for
different test configurations. BIOS/BMC versions are already reported (PWR015);
operators asked for the rest of the configuration (CPU, RAM, board) so a report
is self-describing: "these results were produced on *this* CPU with *this* much
RAM." Centralising it in one shared helper means every current and future test
gets a consistent inventory for free, and there is one place to extend when a
new field is wanted.

## Scope

Shared helpers `function.sh`, `function.py`, `function.ps1`, and every test that
emits a `result.json` / report: `power_cycle.py`, `reboot.py`, `reboot.ps1`,
`net_test.sh`/`.ps1`, `disk_test.sh`, `dev_detect.sh`/`.ps1`, `slp_test.sh`.

## Implications

1. A new `system_info` object is added to the `result.json` schema (LOG015);
   its absence in older result files must be tolerated by report renderers.
2. Fields are populated best-effort; the report shows `N/A` for anything the
   platform/tool could not provide, and marks assumptions (e.g. no BMC present).
3. Collection must be cheap and must not meaningfully delay the test (run once
   per test, cache within the run).
4. Non-compliance must be corrected before merge.

## Verification

Code Review: confirm a single shared `collect_system_info` helper exists per
language with equivalent fields (FWK036); confirm each test writes `system_info`
into `result.json` and the report renders it; confirm missing tools degrade to
`N/A` without failing the test.
