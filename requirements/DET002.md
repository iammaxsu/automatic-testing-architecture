# DET002 — RAM Capacity, DIMM Population & Usability Verification

## Statement

The device-detection test shall report the DUT's memory configuration and assign
a **PASS/FAIL** verdict for it:

1. **Report** — for each populated DIMM slot: slot/locator, size, and (when
   available) type/speed/part-number, plus:
   - `dimm_populated_count` and `installed_total` — the number of populated
     slots and the sum of their sizes, from the DMI/SPD view
     (`dmidecode -t memory` / `Win32_PhysicalMemory`); and
   - `usable_total` — the memory the OS can actually use
     (`/proc/meminfo` `MemTotal` / `Win32_ComputerSystem.TotalPhysicalMemory`).

2. **Usability check (FAIL condition)** — the test shall **FAIL** when the
   OS-usable total is smaller than the DMI-populated total by more than a
   tolerance that normal firmware/kernel-reserved memory can explain. Concretely,
   FAIL when a **whole DIMM's worth or more** of populated memory is missing from
   the usable total, i.e. `installed_total − usable_total` exceeds
   `max(reserved_tolerance, smallest_populated_DIMM_size × 0.5)`, where
   `reserved_tolerance` accounts for the few percent the OS always reserves
   (recommend the larger of ~3% of installed or ~2 GiB). Such a gap means one or
   more DIMMs are **populated but not trained/enabled** — a defective DIMM, slot,
   or seating — even though the machine booted.

3. **Expected-config check (optional FAIL)** — when an expected configuration is
   known (a golden snapshot per DET009/DET012, or an operator-supplied
   `--expected-ram` / config value), the test shall also FAIL when the observed
   populated count or total differs from the expected one.

4. **PASS** — populated DIMMs are all usable (no material gap) and, if an
   expected config is set, the observed config matches it.

`dev_detect.sh` and `dev_detect.ps1` shall implement this equivalently (FWK036).

## Rationale

Reporting DIMM population alone is not enough: a DIMM can be **present but not
working**. Observed on a real DUT — 6 × 32 GB installed, boots into Ubuntu, and
`dmidecode` shows all 6 slots populated (192 GB), but `/proc/meminfo` reports
only 128 GB and the BIOS setup screen likewise shows only 4 DIMMs / 128 GB. Two
DIMMs are populated yet not usable (a training/seating/DIMM fault). A test that
trusts `dmidecode` alone would wrongly PASS. Cross-checking the DMI-populated
total against the OS-usable total catches exactly this class of fault on the
first run, without needing a known-good golden. The tolerance prevents normal
reserved-memory shrinkage (a few hundred MB to ~1–2 GB) from causing false
FAILs, while a whole missing DIMM (tens of GB) is well outside it.

## Scope

`src/bash-shell/dev_detect.sh`, `src/powershell/dev_detect.ps1`, and their shared
detection helpers in `function.sh` / `function.ps1`.

## Implications

1. The memory record in `result.json` shall include `dimm_populated_count`,
   `installed_total`, `usable_total`, the per-DIMM list, the computed gap, and
   the PASS/FAIL verdict with a human-readable reason.
2. Units and rounding must be explicit (report GiB vs GB consistently); the
   comparison is done in bytes to avoid rounding errors, then displayed.
3. `usable_total` is expected to be slightly below `installed_total` even on a
   healthy system; the tolerance in §2 must not be set so tight that reserved
   memory trips it, nor so loose that a whole missing DIMM passes.
4. When `dmidecode` is unavailable or restricted, the test records the fact and
   downgrades the usability check to UNKNOWN (not a silent PASS).
5. Non-compliance must be corrected before merge.

## Verification

Automated Test: on a DUT with all DIMMs healthy, confirm PASS and that
`usable_total ≈ installed_total` within tolerance. Simulate/observe a
populated-but-unusable DIMM (installed_total − usable_total ≥ one DIMM) and
confirm FAIL with a reason naming the gap. Confirm `dmidecode`-absent degrades to
UNKNOWN, not PASS. Confirm `dev_detect.ps1` produces an equivalent verdict.
