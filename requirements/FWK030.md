# FWK030 — Two-Phase Consecutive-Failure Stop Policy

## Statement

Each test script shall apply a two-phase consecutive-failure policy governed by two
independently configurable thresholds:

**Phase 1 — Early abort (before any PASS)**

If the first `EARLY_FAIL_THRESHOLD` consecutive cycles all fail before any cycle
produces a PASS verdict, the test run shall abort immediately. At this point failure
is almost certainly a configuration error (wrong host, DUT offline, bad credentials,
incorrect GPIO pin) rather than a real hardware defect. Continuing would produce
meaningless data and waste time.

Set `EARLY_FAIL_THRESHOLD = 0` to disable early abort entirely.

**Phase 2 — Mid-run (after at least one PASS)**

Once a PASS has been recorded, consecutive failures shall **not** abort the run by
default (`MAX_CONSECUTIVE_FAILS = 0`). A real hardware defect must be characterised
across the full N cycles; failure-rate and distribution charts are only meaningful
over the full run. The test shall continue to completion even if many consecutive
cycles fail mid-run.

Set `MAX_CONSECUTIVE_FAILS > 0` only if a hard mid-run abort limit is explicitly
required (e.g., to stop an infinite hardware failure loop before all N cycles run).

## Rationale

The two phases address fundamentally different failure modes:

- **Pre-PASS failures** are almost always operator errors: the DUT is offline,
  the wrong IP was specified, SSH credentials are wrong, or a GPIO pin is mis-wired.
  Stopping early gives an actionable diagnostic without wasting machine time.
- **Mid-run failures** are the actual test data. Stopping mid-run would discard
  information about failure frequency, distribution across cycles, and boot-time
  trends. The data is valuable precisely because it characterises a real defect.

## Scope

`src/python/power_cycle.py` and `src/python/reboot.py`; defaults in `src/python/config.py`.

## Implications

1. Both `EARLY_FAIL_THRESHOLD` and `MAX_CONSECUTIVE_FAILS` shall be declared in
   `config.py` with their defaults and the matching CLI flag names documented inline.
2. Both scripts expose `--early-fail-threshold N` and `--max-consecutive-fails N`
   CLI arguments that override the config.py defaults at runtime.
3. The scripts shall log a clear diagnostic message identifying which threshold
   triggered the abort and what the likely cause is.
4. A `consecutive_fails` counter resets to zero on each PASS. Transitions between
   phases (first PASS) are tracked via a `has_had_success` boolean.
