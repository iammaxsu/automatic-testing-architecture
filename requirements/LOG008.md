# LOG008 — Discrete-Mode Log Filename Order

## Statement

For tests that run in **discrete mode** (one independent log file per
iteration — see LOG017), the log filename order shall be:

`<test_name>_<n>_of_<m>_<timestamp>_<result>.log`

Example: `net_test_2_of_3_20251001T094630_Pass.log`

Where:
- `<n>` is the iteration number within the session (1-based).
- `<m>` is the total planned iterations for the session (see LOG023).
- `<timestamp>` is ISO 8601 **basic** format `YYYYMMDDTHHmmss` (LOG005,
  LOG022). The `T` separator is mandatory.
- `<result>` is the outcome of that iteration (e.g. `Pass` / `Fail`).

This pattern does **not** apply to continuous-mode tests (e.g.
`power_cycle`), which produce a single log per session named
`<test>_<session>.log`; see LOG017.

## Rationale

Embedding `<n>_of_<m>` and `<result>` in the filename lets an operator
see the progress and outcome of each discrete iteration directly from a
directory listing, without opening files. Discrete mode suits component
detection tests (`dev_detect`) where each run is independent and its
result is known when the run completes.

## Scope

Discrete-mode tests in all scripts and shared libraries.

## Implications

- Non-compliance must be corrected before merge.
- The earlier example `..._20251001094630_Pass.log` (without the `T`
  separator) was a documentation error; `T` is mandatory per LOG005.
- `<result>` is only knowable after the iteration finishes, which is
  compatible with discrete mode (the file is named at completion).
  Continuous-mode tests cannot follow this pattern because their single
  log spans many cycles with mixed results; they record per-cycle
  verdicts inside `result.json` instead (LOG017, option A).
