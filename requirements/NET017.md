# NET017 — Link Quality Metrics and Full-Duplex Throughput

## Statement

For each (interface, speed) under test the framework shall, in addition to the
average throughput of NET006:

1. **Capture iperf3 quality metrics** that iperf3 already reports on every run
   and record them in result.json:
   - TCP retransmissions (forward and reverse),
   - UDP jitter (ms) and UDP packet loss (%) (forward and reverse).

2. **Measure simultaneous bidirectional (full-duplex) throughput** — both
   directions carrying traffic at the same time — and record each direction
   and their sum. A link that passes one-direction-at-a-time but collapses
   under simultaneous bidirectional load reveals a PHY, PCIe, or bus
   bottleneck that the unidirectional NET006 runs cannot.

These metrics are recorded and rendered alongside the per-speed verdict; they
inform the verdict reason (NET008) and may be used by future threshold rules
(NET009).

## Rationale

Average Mbps is necessary but not sufficient for world-class link validation.
Retransmits, jitter, and loss expose a marginal link that still averages an
acceptable rate; full-duplex throughput is the only test that actually loads
both directions of the wire at once, which is how the link is used in
production. Because iperf3 already computes the quality figures, collecting
them is essentially free.

## Scope

All scripts and shared libraries in the framework.

## Implications

1. TCP retransmits and UDP jitter/loss are recorded per direction per speed.
2. A simultaneous bidirectional throughput pass is run per speed and its
   per-direction and summed results recorded.
3. Both are shown in the rendered report and feed the verdict reason.
4. The bidirectional pass is config-gated (SET001) so it can be disabled on
   time-constrained runs.
5. **Platform limitation (TCP retransmits on Windows):** the Windows iperf3
   builds do not expose the kernel's TCP retransmit counter, so the sender
   summary line has no `Retr` value. `tcp_fwd_retr` / `tcp_rev_retr` are
   recorded as `null` in this case, and the report renders `-` with a
   "retr N/A on Windows" note instead of a blank cell. UDP jitter/loss remain
   available and reliable on both platforms and should be the primary quality
   signal on Windows. Linux iperf3 reports TCP retransmits normally.
6. **Measurement robustness:** before launching each iperf3 client the
   framework shall confirm the iperf3 server is actually accepting connections
   on its control port (an active TCP probe, not a fixed sleep), and shall
   retry a direction that returns no data — restarting the server first — up to
   a small fixed number of attempts. This prevents a transient server-start
   race (most visible right after a link-speed change forces an adapter
   restart) from producing a spurious `UNKNOWN` verdict (NET008) on an
   otherwise healthy link.
7. **Stale-server cleanup:** the regular per-direction tests and the
   bidirectional pass share a port (the bidirectional pass's even→odd server
   uses the same port as the regular tests). Before each speed's iperf block,
   and again after the bidirectional pass, the framework shall force-kill any
   iperf3 process still running for that pair. Otherwise a server left over
   from a previous loop's bidirectional pass can keep that port "open" so the
   readiness probe (implication 6) reports ready against the stale process,
   and every retry hangs against it with "Connection timed out" instead of
   reaching the freshly started server.
8. Non-compliance must be corrected before merge.
