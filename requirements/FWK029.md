# FWK029 — Emergency Stop Safety Mechanism

## Statement

The framework shall provide an immediately-executable emergency stop mechanism
that halts all running tests on both the control node and the DUT within a
predictable, short time. No test run shall be able to enter or sustain an
unrecoverable state (such as an infinite reboot loop) without an accessible
manual override that a single person can invoke.

## Rationale

Hardware endurance tests control real physical hardware: relays, PSUs, and
OS-level reboots. A software defect or operator error can cause the DUT to
enter a destructive loop (e.g., continuous power cycling or rebooting) that
damages hardware, corrupts the OS, or exhausts GPIO hardware before anyone can
intervene manually.

A dedicated emergency stop removes the dependency on system-level interventions
such as unplugging power or resetting the Pi, both of which can corrupt in-flight
writes. It also provides a deterministic audit trail: the stop is recorded in the
session file and the log, so the exact cycle at which the test was halted is
preserved.

## Scope

| Component               | Stop mechanism                                               |
|-------------------------|--------------------------------------------------------------|
| Pi — Python processes   | `stop_tests.sh`: sends SIGINT to `power_cycle.py`/`reboot.py` |
| DUT — PowerShell test   | `reboot.ps1 -Stop`: writes `reboot_stopped.flag` sentinel    |
| Composite test run      | `stop_tests.sh --host … --dut-ps1 …`: stops both in one call |

## Implications

1. **Single-command stop**: a single invocation of `stop_tests.sh` (with
   appropriate options) shall stop all running test processes on the Pi and
   optionally on the DUT via SSH.

2. **Sentinel persistence**: the stop decision shall be durable across process
   restarts. On the DUT, `reboot_stopped.flag` prevents `reboot.ps1` from
   auto-starting a new session even after a reboot triggered by Task Scheduler.
   The sentinel is only cleared by an explicit `-Cycles N` argument.

3. **Graceful termination**: SIGINT to Python processes triggers the existing
   `_stop_requested` logic, which finishes the current cycle cleanly, writes
   the final `result.json`, and generates the HTML report before exiting.
   This preserves all data collected up to the stop point.

4. **Audit trail**: the stop event shall be recorded:
   - Python side: the process exits with `overall_verdict = FAIL` (or `PASS`
     if all completed cycles passed) and writes the final report.
   - PowerShell side: `SESSION_STOPPED` is appended to the cycle log, the
     session status is set to `stopped`, and `REBOOT_STATUS.txt` is updated.

5. **No silent auto-restart after stop**: once `-Stop` has been issued, the DUT
   Task Scheduler trigger shall exit silently on every subsequent boot until
   `-Cycles N` is explicitly provided.

6. **Documentation**: the `--help` output of every test script shall document
   the stop procedure. For DUT-local tests, the `.DESCRIPTION` comment block
   in the `.ps1` file shall include a "STOPPING A TEST" section.

7. **Composite workflow**: when `run_tests.sh` is used to run Python-controlled
   tests against a DUT that also has `reboot.ps1` registered in Task Scheduler,
   `reboot.ps1 -Stop` should be issued on the DUT before starting the Python
   test to prevent the DUT from auto-starting its own conflicting session.

## Verification

- Code review of `stop_tests.sh`, `reboot.ps1 -Stop` sentinel logic, and
  SIGINT handler in `power_cycle.py` / `reboot.py`.
- Manual test: start a test, invoke the emergency stop, confirm all processes
  halt within one cycle boundary (≤ the configured boot timeout), and confirm
  the sentinel file is present and the session status is `stopped`.
- Reboot test: after `-Stop`, reboot the DUT; confirm Task Scheduler fires but
  `reboot.ps1` exits silently without starting a new session.
