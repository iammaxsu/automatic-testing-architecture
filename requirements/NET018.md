# NET018 — Jumbo Frame (MTU) Verification

## Statement

At each link speed of 1000 Mbps or higher the framework shall verify that a
jumbo frame crosses the link unfragmented: it shall raise the MTU on both NICs
in the pair to a configurable jumbo size (`_net_jumbo_mtu`, default 9000 bytes),
send a Don't-Fragment ICMP echo of payload `MTU − 28`, record PASS only if a
reply is received without fragmentation, then restore the standard MTU.

The jumbo result is recorded per (interface, speed) in result.json and shown in
the rendered report as one of `PASS`, `FAIL-FRAG` (DF packet could not be sent
or was rejected as too large for the path MTU), `FAIL` (no reply for another
reason), `SKIP` (the NIC/driver does not support a frame large enough for the
configured jumbo MTU, so the test was not attempted), or `UNKNOWN` (the MTU
change itself failed). By default a jumbo result other than PASS or SKIP is
informational (annotated in the verdict reason, NET008) and does not by itself
fail the speed verdict.

## Rationale

Jumbo-frame support is a common requirement for storage, virtualisation, and
high-throughput workloads, and is a frequent source of silent
misconfiguration (one end not configured, an intermediate device clamping the
MTU). A DF-bit ping at the jumbo payload size is the standard, cheap end-to-end
proof that the full frame traverses the link. It is only meaningful at gigabit
and above, hence the speed gate.

## Scope

All scripts and shared libraries in the framework.

## Implications

1. MTU is raised on both NICs, tested with a DF jumbo ping, and restored, at
   each >=1000M speed.
2. The jumbo size is configurable (SET001).
3. The result is recorded and rendered; failures annotate the verdict reason.
4. The feature is config-gated so it can be disabled.
5. Non-compliance must be corrected before merge.
