# LOG023 — Test Session Identity and Resume

## Statement

Every test run shall belong to a **session** identified by a
`session_id` (the session's start time in ISO 8601 basic format,
`YYYYMMDDTHHmmss`). A session has a planned iteration count `m` and a
completed iteration count `n`. The framework shall persist session state
in a session file so an interrupted session can be resumed.

### Session state file

A JSON file `<test>_session.json` in the session directory shall record:

```json
{
  "session_id": "20260601T174545",
  "test": "power_cycle",
  "m": 10,
  "n": 6,
  "status": "running",
  "started_at": "2026-06-01T17:45:45",
  "updated_at": "2026-06-01T18:30:12"
}
```

`status` is `running` while `n < m`, and `complete` once `n == m`. The
file shall be written atomically (write `.tmp`, then rename) after every
iteration.

### Resume rule

On startup, the framework shall inspect `<test>_session.json`:

- If it exists with `status == running` and `n < m` (and `--new-session`
  is not given), the run shall **resume** that session: reuse the same
  `session_id`, log file, and `result.json`; continue from iteration
  `n + 1` up to `m`; append to the existing artefacts.
- Otherwise the run shall start a **new** session: `session_id` = current
  time, `n = 0`, `m` = the requested iteration count.

### Mapping to operator scenarios

| Scenario | Invocation | Result |
|----------|-----------|--------|
| Continuous 10, one batch | one run with `m = 10` | single session, `n` 1→10 |
| 5 today + 5 tomorrow, one batch | `m = 10`, interrupted at `n = 5`, rerun next day | auto-resume `n` 6→10 |
| 10 runs, each its own batch | ten runs with `m = 1` | ten sessions |
| 5 today + 5 tomorrow, two batches | `m = 5` today (completes), `m = 5` tomorrow | two sessions |

## Rationale

Endurance runs can span days or be interrupted by power loss. Persisting
`(session_id, m, n, status)` plus the incrementally-written `result.json`
(LOG017 continuous mode) means completed iterations and their verdicts
are never lost, and a rerun transparently continues where it stopped
rather than discarding progress or double-counting. The `n`/`m` pair also
feeds discrete-mode filenames (LOG008) and keeps a composite run's
continuous and discrete artefacts aligned on the same iteration index
(LOG024).

## Scope

`src/python/function.py` (session read/write helpers),
`src/python/power_cycle.py` (resume logic); future `reboot` and any other
continuous-mode test. Discrete-mode tests consume the same `n`/`m`.

## Implications

- A new session file `<test>_session.json` is created per test in the
  session directory.
- `--new-session` forces a fresh session even if an incomplete one exists.
- On resume, warmup (PWR008) is skipped (the counted test is already
  under way); initial-state normalization still runs to re-establish a
  known DUT state.
- If the requested iteration count differs from the resumed session's
  stored `m`, the stored `m` wins and a warning is logged.
- `result.json` `config.cycles_target` equals the session `m`.

## Verification

Automated Test: start a run with `m = 4`, interrupt after 2 cycles,
rerun; confirm the second invocation logs "Resuming session …", continues
at cycle 3, and the final `result.json` contains 4 cycles under one
`session_id`. Run again; confirm a new session starts.
