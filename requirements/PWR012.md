# PWR012 — Pi-Side Reboot Test (`reboot.py`)

## Statement

`reboot.py` shall implement a reboot endurance test controlled from the Pi (control
node), mirroring the structure of `power_cycle.py` but using SSH software reboot
instead of a GPIO relay:

1. **Cycle structure**: Each cycle shall consist of:
   - SSH to DUT and issue `sudo reboot`.
   - Wait for the DUT to go offline (liveness check).
   - Wait for the DUT to come back online (liveness check, bounded by
     `BOOT_TIMEOUT_SEC`).
   - Record verdict: **PASS** if the DUT comes online within the timeout; **NO_BOOT**
     otherwise.
   - `boot_time_sec` records the reboot **round-trip** — `t_online - t_reboot_cmd`,
     i.e. the time from issuing the reboot command to the DUT being confirmed alive
     again (shutdown + POST + boot) — the same definition PWR011 §3 gives for
     `reboot.ps1`. It must be measured end-to-end, not as the duration of a single
     polling call inserted after an unrelated fixed sleep (BUG0027).

2. **CLI interface**: `reboot.py` shall accept the same options as `power_cycle.py`
   where applicable:

   | Option | Default | Meaning |
   |--------|---------|---------|
   | `--host` | `DUT_HOST` | DUT IP / hostname |
   | `--cycles N` | `CYCLES` | Number of reboot cycles |
   | `--off auto\|SECONDS` | `auto` | Inter-cycle delay after the verdict is recorded (see Implications §7) |
   | `--boot-timeout SECONDS` | `BOOT_TIMEOUT_SEC` | Max wait for DUT to come back |
   | `--ssh-user USERNAME` | `SHUTDOWN_SSH_USER` | SSH login (required for reboot) |
   | `--out DIR` | `LOG_DIR` | Output directory |
   | `--new-session` | — | Force new session (LOG023) |
   | `--debug` | — | Stop immediately on the first non-PASS cycle, leaving DUT state as-is for inspection (see Implications §8) |
   | `--pin N` | `GPIO_PIN` | GPIO pin for init power recovery (FWK031/PWR013) |
   | `--type ATX\|AT` | `POWER_TYPE` | PSU type for init power recovery (FWK031/PWR013) |
   | `--init-wait SECONDS` | `INIT_WAIT_SEC` | GPIO-unavailable fallback wait (FWK031/PWR013) |
   | `--dry-run` | — | Simulate without SSH |

3. **Session / resume** (LOG023, LOG025): Same mechanism as `power_cycle.py`,
   sharing `function.resolve_session()`. Session directory:
   `logs/<dut_id>/reboot_<session_id>/`, where `<dut_id>` defaults to a
   slugified `--host` (override with `--dut-id`). Inside that directory:
   - Session state: `meta.json`
   - Log: `reboot_<session_id>.log`
   - Result: `reboot_<session_id>.result.json`
   - `session_id` uses ISO-8601 basic format (`YYYYMMDDTHHmmss`, LOG022).

4. **Shared utilities**: `reboot.py` shall reuse `function.py`, `liveness.py`,
   `config.py`, and `report.py` from `power_cycle.py`. No GPIO / relay interaction
   occurs. On completion it shall render `reboot_<session_id>.report.html` from the
   canonical `result.json` via the shared `report.py` (FWK028 / LOG018).

5. **Composite test**: `reboot.py` is designed to run sequentially after
   `power_cycle.py` (or standalone). No shared session state between the two tests
   is required; each produces its own session and log files.

## Rationale

`power_cycle.py` tests hardware power loss recovery; `reboot.py` tests software
reboot stability (OS shutdown path, driver unload/reload, filesystem integrity on
clean reboot). Running both back-to-back in a composite test maximises coverage of
reliability failure modes without requiring additional hardware beyond the SSH
connection already used for graceful shutdown in `power_cycle.py` (PWR009).

## Scope

`src/python/reboot.py` (new); `src/python/config.py` (shared defaults reused).

## Implications

1. `--ssh-user` is mandatory at runtime (reboot requires SSH; there is no relay
   fallback). The script shall abort with a clear error if `--ssh-user` is empty.
2. Init phase (FWK031/PWR013): before the first cycle `reboot.py` calls
   `function.init_dut()` to normalise DUT state. If the DUT is offline it is powered on
   via GPIO (escalating to a forced power cycle if a power-on press is not enough);
   when no GPIO pin is configured it falls back to waiting `--init-wait` seconds for a
   still-booting DUT. See FWK031 for the escalation contract and PWR013 for the
   reboot-specific application.
3. Consecutive-failure abort (`MAX_CONSECUTIVE_FAILS`) applies as in `power_cycle.py`.
4. A simple composite run script (e.g., `run_tests.sh`) can call `power_cycle.py` then
   `reboot.py` sequentially; each produces its own log/session directory.
5. Each cycle shall ping the DUT **before** issuing the SSH reboot command. SSH
   returns exit 255 both for a successful reboot (connection dropped as the OS goes
   down) and for a refused connection (DUT already powered off); the two are
   indistinguishable by exit code alone. A failed pre-reboot ping therefore yields an
   immediate `SSH_ERROR` rather than a false "reboot sent" followed by a spurious
   `NO_BOOT` after the boot timeout expires.
6. **Deriving timing parameters empirically, not by rule of thumb.** `BOOT_TIMEOUT_SEC`,
   `OFF_TIME_SEC`, `DEAD_TIMEOUT_SEC` (and `reboot.ps1`'s `REBOOT_SETTLE_SEC`) are
   currently set from rule-of-thumb guesses spread across `config.py` and each
   script's own defaults. They do not have to be: `power_cycle.py` already produces
   statistically sound boot-time and shutdown-time distributions in its canonical
   `result.json` / rendered report (FWK028), and these can be read directly off a
   real run to set the bounding parameters for the *next* run on the same DUT/OS
   combination — e.g. `BOOT_TIMEOUT_SEC ≈ max(boot_time_sec) + margin`,
   `DEAD_TIMEOUT_SEC ≈ max(shutdown completion) + margin`. Observed on the Windows 11
   DUT used for the 2026-06-05/06 chained run (`power_cycle_report_20260605T162532.html`,
   `power_cycle_report_20260606T192643.html`, 300 cycles each): boot time
   min 25.3 s / median 45.6 s / mean 45.4 s / max 45.8 s / std-dev 2.0 s; shutdown
   time min 15.1 s / median ~21–22 s / mean ~19 s / max ~22.4 s / std-dev ~3.4–3.5 s.
   Against these, the current defaults (`BOOT_TIMEOUT_SEC=120`, `DEAD_TIMEOUT_SEC=30`)
   carry roughly 2.6x and 1.3x headroom over the observed maxima — adequate, and not
   in need of urgent change, but now backed by data rather than guesswork.
   `reboot.py`'s own `boot_time_sec` now measures the true round-trip (BUG0027 fixed),
   so a `reboot.py` pilot run's own report is itself a valid source for tuning
   `BOOT_TIMEOUT_SEC`, alongside `power_cycle.py`'s statistics.
   **Recommended workflow**: before committing to a long endurance run on a new
   DUT/OS combination, run a short pilot (e.g. 10–30 cycles), read the boot/shutdown
   statistics from its rendered report, and derive that DUT's timeout/settle values
   from them — rather than starting the long run on guessed defaults.
7. **`--off` default is event-driven, not a fixed wait.** Boot detection
   (`wait_until_alive()`) already ends the instant the DUT responds to ping+SSH —
   it does not need a fixed wait of its own to "find" when the DUT is ready. The
   default `--off auto` therefore adds only a short, fixed settle
   (`REBOOT_AUTO_SETTLE_SEC`, 5 s) after that detection — long enough for sshd/sudo
   to finish stabilising in the first instant SSH responds — and then issues the
   next reboot immediately, rather than padding every cycle with a long fixed gap.
   An explicit `--off N` overrides this with a literal N-second fixed delay (`N=0`
   disables the gap entirely), preserved for operators who deliberately want extra
   dwell time between cycles. This is a distinct concept from `OFF_TIME_SEC`, which
   `function.init_dut()` still uses unconditionally (independent of `--off`) for the
   unrelated "how long to stay powered off" duration during a forced power-cycle
   recovery (FWK031 Step 3).
8. **`--debug` for live failure inspection (ported from `power_cycle.py`).** By
   default, `MAX_CONSECUTIVE_FAILS = 0` means mid-run consecutive failures never
   auto-abort — a real hardware defect (e.g. a DUT stuck at POST) must be
   characterised across the full run rather than stopped mid-way, since the
   failure-rate and distribution charts are only meaningful over the complete
   cycle count. This means an unattended run can spend its remaining cycles
   spinning through `SSH_ERROR`/`NO_BOOT` verdicts in quick succession once the
   DUT stops responding, producing no further useful data (observed 2026-06-25:
   145+ such cycles after a DUT hung at POST). `--debug` is the escape hatch for
   an *attended* run: it stops immediately on the first non-PASS cycle, overriding
   both `--early-fail-threshold` and `--max-consecutive-fails`, and leaves the DUT
   untouched for inspection rather than continuing to issue reboot commands at it.
   `result.json` records `config.debug_mode` and, when triggered, a top-level
   `debug_stop: {n, verdict}` block — both already rendered by the shared
   `report.py` (FWK028), unchanged by this addition.

## Verification

Automated Test: run `reboot.py --dry-run --cycles 3 --ssh-user testuser --host 10.0.0.1
--no-check` and confirm:
- Log file `reboot_<session_id>.log` is created.
- `reboot_<session_id>.result.json` contains 3 cycle entries all with verdict `PASS`.
- `reboot_<session_id>.report.html` is rendered from the result.json with the
  boot-time trend and distribution charts.
- Interrupt at cycle 2, rerun without `--new-session` → resumes at cycle 3 under the
  same `session_id`.

**Operator run, 2026-06-06** (Windows 11 DUT, `--cycles 300 --ssh-user … --host …`,
chained immediately after a `power_cycle.py` 300-cycle stage and followed by another):
`reboot_20260606T103112.report.html` — 300/300 PASS, overall verdict PASS, no
failures, `report.py` rendered the trend/histogram/donut charts correctly. This
confirms the cycle structure, session/resume bookkeeping, and reporting pipeline
all work end-to-end (LOG023, FWK028). The one defect found in this run —
`boot_time_sec` reporting a near-constant ~1.0–1.1 s instead of a real round-trip —
is tracked separately as BUG0027 and does not affect the PASS/NO_BOOT verdict
logic itself.
