# PWR011 — DUT-Local Reboot Test (`reboot.ps1`)

## Statement

`reboot.ps1` shall implement a self-contained reboot endurance test that runs entirely
on the DUT without requiring a control node:

1. **Session start** (`-Cycles N`): When invoked manually and **no** running
   session exists, the script shall create a session file
   (`logs/reboot_session.json`) recording `session_id`, `m` (target cycle count,
   from `-Cycles N` or the default), `n = 0`, and `status = "running"`, then
   immediately issue `Restart-Computer`. A running session always takes
   precedence over `-Cycles` (see §4); `-NewSession` forces a fresh session.

2. **Cycle recording**: On each subsequent boot, Task Scheduler invokes
   `reboot.ps1 -Resume` automatically (the `-Resume` entry point, see §5). The
   script shall:
   - Read the session file; if `status != "running"` or `n >= m`, exit without
     action (normal boot, no test in progress). Under `-Resume` this exit is
     silent — it must never start a new session.
   - Record the cycle: `n++`, write a one-line entry to the per-session log file.
   - Verdict: **PASS** = `reboot.ps1` was successfully invoked by Task Scheduler
     (i.e. the DUT completed POST and booted far enough to run the script).
   - If `n < m`: issue `Restart-Computer` after a configurable settle delay
     (`REBOOT_SETTLE_SEC`, default 30 s).
   - If `n >= m`: set `status = "complete"` in the session file and stop.

3. **Artefacts** (LOG022 / LOG023 naming; FWK028 canonical-first):
   - Canonical result:  `logs/reboot_<session_id>.result.json` (same schema as
     `reboot.py`, schema_version 1.1) — the single source of truth, updated
     after every cycle.
   - Per-session log:   `logs/reboot_<session_id>.log` (human-readable).
   - Session state:     `logs/reboot_session.json` (resume bookkeeping only).
   - Plain-text status: `logs/REBOOT_STATUS.txt` (rewritten each cycle).
   - `session_id` uses ISO-8601 basic format (`YYYYMMDDTHHmmss`, LOG022).

   Each cycle record stores `boot_time_sec` as the reboot **round-trip**
   (time from the previous reboot command to the script running again =
   shutdown + POST + boot). The first cycle has no prior reboot to measure
   against, so its `boot_time_sec` is `null`.

3a. **HTML report** (FWK028): the canonical `result.json` is rendered to
   `reboot_<session_id>.report.html` by the shared Python renderer
   (`report.py`), not by `reboot.ps1` itself. `reboot.ps1` never embeds chart
   logic — it only produces the canonical JSON. The report is generated by
   running `python report.py logs\reboot_<session_id>.result.json` on the DUT
   (Python required) or on any machine with access to the JSON.

4. **Resume precedence** (LOG023): A running session (`status = "running"`,
   `n < m`) **always wins**. Whenever one exists and `-NewSession` was not given,
   `reboot.ps1` resumes it from `n + 1` under the same `session_id` (same log and
   result files) and the **stored `m` is kept** — any `-Cycles` value supplied on
   that invocation is ignored (a warning is logged if it differs). `-NewSession`
   discards the running session and starts fresh.

5. **Entry points and Task Scheduler registration**: `reboot.ps1` distinguishes a
   human start from an automatic boot trigger by argument, not by task state:
   - `-Resume` — the Task Scheduler entry point. Resume a running session;
     otherwise **exit silently, never starting a new test**.
   - `-Cycles N` / no args — human start. Resume if a session is running
     (§4); otherwise start a new session (`-Cycles N`, or the default count).
   - `-NewSession` — force a brand-new session even if one is running.
   - `-Stop` — mark the running session `stopped` so `-Resume` will not pick it up.

   `setup_dut.ps1` shall register `reboot.ps1` as a startup Task Scheduler task
   (as SYSTEM, highest privileges) whose action runs **`reboot.ps1 -Resume`**. The
   task is registered **enabled and stays enabled permanently**; the `-Resume`
   entry point's silent-exit behaviour is what prevents it from disturbing a
   normal boot or a Pi-controlled test (BUG0026). `reboot.ps1` itself never needs
   to enable or disable the task, so it runs correctly non-elevated (over SSH or a
   normal local shell).

## Rationale

Power-off/on cycling (controlled externally via relay) and software reboot represent
different hardware failure modes. A DUT can pass 1000 power cycles yet fail on the
100th software reboot due to a driver hang or filesystem corruption. Running the reboot
test on the DUT itself means no control-node infrastructure is required, making it
usable in environments where only the DUT is present.

## Scope

`src/powershell/reboot.ps1` (new); `src/powershell/setup_dut.ps1` (updated to
register the Task Scheduler task and, optionally, to install Python and create
a one-click report launcher); `src/python/report.py` (shared renderer).

## Implications

1. **Always-enabled task, behaviour gated in-script** — `DUT-Reboot` is registered
   **enabled** by `setup_dut.ps1` and stays enabled. The task action is
   `reboot.ps1 -Resume`, which resumes a running session and otherwise exits
   silently. Safety against firing during a normal boot or a Pi-controlled test
   (`power_cycle.py`, `reboot.py`) comes from that silent-exit behaviour, **not**
   from toggling the task's enabled state. This keeps `reboot.ps1` runnable
   non-elevated (enabling/disabling a SYSTEM task would require elevation, which
   the SSH and local execution paths do not have). BUG0026 documents the original
   defect (an always-enabled task that started a rogue default session) and this
   resolution.
2. A test started manually (`reboot.ps1 -Cycles 1000`) will reboot the DUT
   immediately — warn the user in the script header.
3. The settle delay (`REBOOT_SETTLE_SEC`) prevents immediately re-rebooting before
   the OS finishes writing logs from the previous boot.
4. `dev_detect.ps1` also runs at startup (registered separately); the two scripts run
   independently and each produce their own log.
5. The HTML renderer (`report.py`) is shared with `power_cycle.py` and `reboot.py`;
   adding or changing a chart is done in one place. This requires Python on whatever
   machine renders the report (the DUT, if reports are generated locally).
6. `setup_dut.ps1` unconditionally installs Python on the DUT (winget first,
   python.org silent installer as fallback) and downloads `report.py` from GitHub
   into the same folder as `reboot.ps1`. After `setup_dut.ps1` runs once, the DUT
   is fully self-contained: no manual Python install or file copying is needed.

## Verification

Automated Test: run `reboot.ps1 --cycles 3 --dry-run` (dry-run mode skips actual
`Restart-Computer`) and confirm:
- `reboot_session.json` is created with `m=3, n=0, status="running"`.
- Manually calling `reboot.ps1` (simulating the 3 Task Scheduler triggers) increments
  `n` to 3 and sets `status="complete"`.
- Log file `reboot_<session_id>.log` contains 3 cycle entries.
- `reboot_<session_id>.result.json` contains 3 PASS cycle entries and
  `overall_verdict="PASS"`; `python report.py reboot_<session_id>.result.json`
  produces a `.report.html` with the boot-time trend and distribution charts.
