# PWR014 — Empirically-Derived Reliability-Test Timing Parameters

## Statement

Timing parameters used by the reliability tests (`power_cycle.py`, `reboot.py`,
`reboot.ps1` — e.g. `BOOT_TIMEOUT_SEC`, `DEAD_TIMEOUT_SEC`, `OFF_TIME_SEC`,
`REBOOT_SETTLE_SEC`) shall be derived from measured boot/shutdown statistics on
the actual DUT/OS combination under test, rather than fixed rule-of-thumb
defaults shared across all hardware:

1. Before committing to a long endurance run on a new DUT/OS combination, run a
   short pilot (e.g. 10–30 cycles), then read the boot-time and shutdown-time
   statistics from the pilot's rendered report (FWK028 canonical `result.json`
   → `report.py`).
2. Derive that DUT's parameter values from the pilot statistics — but the two
   classes of parameter must be tuned in **opposite directions** (see
   Implications #1): "fixed wait" parameters close to the observed value;
   "timeout / upper-limit" parameters with generous margin above the observed
   maximum.
3. (Open for discussion — see Implications #3) the exact derivation formula,
   margin multiplier, and whether tooling should compute suggested values
   automatically from a pilot's `result.json` are not yet decided.

## Rationale

Today's defaults in `config.py` and each script's CLI defaults were set by rule
of thumb / guesswork, as noted while documenting the 2026-06-05/06 chained
900-cycle run (PWR011/PWR012 verification). `power_cycle.py` already produces
statistically sound boot-time and shutdown-time distributions in its canonical
`result.json` (FWK028) — e.g. on the Windows 11 DUT used for that run: boot time
median 45.6 s / max 45.8 s / std-dev 2.0 s; shutdown time median ~21–22 s /
max ~22.4 s / std-dev ~3.4–3.5 s. There is no need to keep guessing when a short
pilot run yields exactly the numbers needed to set the full-scale run's
parameters correctly for that specific hardware.

## Scope

`src/python/config.py` (defaults); CLI defaults in `power_cycle.py`, `reboot.py`;
`src/powershell/reboot.ps1` (`REBOOT_SETTLE_SEC` and friends); potentially a new
helper that reads a pilot run's `result.json` and suggests parameter values.

## Implications

1. **The two parameter classes tune in opposite directions** — this is the
   central insight and must not be lost in any future automation:
   - *Fixed-wait* parameters (`OFF_TIME_SEC` as an inter-cycle delay,
     `REBOOT_SETTLE_SEC`) directly add to every cycle's runtime regardless of
     outcome — set them close to the observed required value to avoid wasting
     time across thousands of cycles.
   - *Timeout / upper-limit* parameters (`BOOT_TIMEOUT_SEC`, `DEAD_TIMEOUT_SEC`)
     do **not** affect a successful cycle's runtime at all — the test proceeds
     the instant the DUT responds. Their only cost is how long a *genuine*
     failure takes to be declared. Setting them too tight risks misclassifying
     a legitimately-slow-but-healthy boot (long-tail events: fsck, pending
     updates, driver hiccups) as `NO_BOOT` / `HANG_SHUTDOWN`, polluting the
     endurance data with false failures. These should therefore carry generous
     margin — e.g. ~2x the observed maximum — at essentially no cost.
2. This requirement formalises the "small pilot, then scale" workflow already
   recommended informally in PWR012 Implications #6; that note should be
   superseded by / merged into this requirement once its details are settled.
3. **Open questions for later discussion** (hence `status: proposed`): the
   precise derivation formula and margin multiplier to standardise on (e.g.
   `max + 2×max`? `p99 + fixed margin`? per-parameter rules?); whether to build
   a helper script that reads a pilot's `result.json` and prints suggested
   `config.py` values; how many pilot cycles are "enough" to trust the
   statistics; and whether/how these derived values should be recorded
   alongside the full-scale run's artefacts for traceability.

## Verification

Not yet defined — depends on the open questions in Implications #3. Likely
Code Review of the documented derivation guidance, plus a worked example
showing pilot-run statistics → derived parameter values → full-scale run
confirming no false failures and acceptable total runtime.
